## 2. Database Structure

All tables live in the `public` schema of the Supabase Postgres database (project `ascend-now`, ref `uqyuczvckqxgtilpzarh`). **Full column-by-column detail, constraints, RLS policies, functions, and triggers live in [`db/docs/VERIFIED_DATABASE_STATE.md`](./db/docs/VERIFIED_DATABASE_STATE.md)** — that file is regenerated by direct introspection of the live database and is the only schema doc that should be trusted. What follows here is a map of what exists, grouped by feature area.

### 2.1 Identity & access
`users` (1-to-1 with `auth.users`, no password stored — Supabase Auth owns that), `teachers` (a performance coach is a teacher with `is_performance_coach = true`), `teacher_subjects` (junction: teacher ↔ subject ↔ curriculum), `admins` (minimal — access comes from `users.role = 'admin'`). `student` has its own read-only dashboard (see §3.7). As of 2026-07-07, **there is no separate `parent` role or `parents` table** — the student/parent dashboard merge removed both; a student now has exactly one login, and the former parent/guardian's name and phone are kept as plain fields directly on the `students` row (`parent_full_name`/`parent_phone_number`) rather than a linked account. A SECURITY DEFINER `can_view_student()` function scopes student read policies (its old parent-lookup branch was removed along with the role).

As of 2026-07-04, teachers/coaches are deactivated exclusively through the `deactivate-teacher-with-user` edge function (not a bare table update): it refuses to deactivate a performance coach who still has an active `pc_student_assignments` row (reassign the student first). It does not touch the teacher's login email or `teachers.email` in any way — a same-day attempt to free up a deactivated teacher's email for reuse was reverted, since reactivating that account later (the underlying capability exists but has no UI today) would come back with a broken email once the real address belonged to a different, newer teacher. `teachers.email` stays globally unique.

### 2.2 Session logging
`session_logs` — the core teacher session-logging table. `session_no` (manual sequence number) has been **dropped entirely**. Student identification moved from free-text name columns to a proper `student_id` FK (the old `student_first_name`/`student_last_name` columns still exist, now nullable, kept for backward compatibility). Sessions link to `subjects`, `curricula`, `program_types`, and `course_types`, and carry Fathom-derived fields (`fathom_summary`, `engagement_rating`, `performance_feedback`, `flag_for_coach`) and no-show tracking (`no_show_type`).

As of 2026-07-04, the three `no_show_type` values behave differently for billing/payout purposes (see `src/utils/noShow.ts` for the shared predicates every consuming page uses): **No Show 1** affects neither the student nor the teacher. **No Show 2** pays the teacher a fixed rate (`no_show_settings.payout_amount`, admin-editable from Admin → Reports → Settings) but doesn't touch the student's package. **No Show +** does both — it pays the teacher the same fixed rate *and* still deducts an hour from the student's package. All three no-show types now ask for Type of program and Subject just like a real session (kept, not reset, if already picked before marking the no-show) — only `course_type_id`/`session_duration_hrs`, the fields the package-deduction trigger and hour totals actually key off, stay populated for No Show + alone; they're null for No Show 1/2 so those two never bill regardless of the program type/subject on file. Each teacher's payable no-show count and resulting payout are shown on the Admin Reports "Teacher Hours" tab and on the teacher's own "My Hours" page, and snapshotted onto `monthly_report_teacher_stats` (`no_show_payable_count`/`no_show_payout_amount`) when a monthly report is generated/locked.

As of 2026-07-06, **no no-show type of any kind (No Show 1, No Show 2, No Show +) ever asks for a duration in the session-log form**, for teacher or admin — the "Session duration" dropdown only appears for a regular session. **No Show +** (the one no-show type that still bills) picks up its duration purely from a single admin-editable constant (`session_duration_settings.default_duration_hrs`, defaults to 1 hour, same single-row-settings pattern as `no_show_settings`) applied automatically the moment No Show + is picked; it is never shown or editable in the form itself. Admins change both no-show constants — the payout rate and the default duration — from the **Settings** tab of `/admin/reports`. An existing logged session keeps whatever duration it already has when edited. See `db/docs/VERIFIED_DATABASE_STATE.md`.

`program_types` is a 2-level hierarchy (`parent_id` self-FK). As of 2026-07-01, offline work is split at the top level: **Ascend Offline Work** is its own standalone top-level type — no student, no package deduction, just topic + a note — and **Student Offline Work** is a top-level group with two sub-programs, **Academic Offline Work** / **Beyond Academic Offline Work** (student required, bills against the matching course type same as a regular session). `ECA/School collaboration`, `Others`, and `Work for Ascend Now` have been removed as unused. The session-log forms (teacher and admin) both render the same shared `src/components/sessionLogs/SessionLogFormView.tsx`, which keys off `type` (`ascend_offline_work` / `student_offline_work` at the top level, `academic_offline_work` / `beyond_academic_offline_work` as sub-programs) to drive this behavior. **College Counselling** (top-level `type = 'college_counselling'`) is a standalone type with **no sub-programs** as of 2026-07-09 — it used to have two (`College Counselling` / `College Essays`, now deactivated `program_types` rows), which are now plain `subjects` instead, picked exactly like Beyond Academic's flat subject list (see `db/docs/SUBJECT_HIERARCHY.md` §3b). `course_types`/bundle-pool billing for College Counselling is unaffected by that move.

As of 2026-07-02, **College Counselling** is a further top-level type with two sub-programs, **College Counselling** (same name as its parent — see below) / **College Essays** — both bill against the `course_types` row named "College Counselling" (a plain per-parent-name match, no extra `type`-based special-casing needed since a `course_types` row with that exact name already existed, just inactive). `program_types.name` used to be globally unique, which would have blocked a sub-program sharing its parent's exact name — that was relaxed the same day to a per-parent unique index so this works.

As of 2026-07-23/24, logging **Ascend Offline Work** also asks "Assigned by" — a required Teacher dropdown recording who assigned the offline work, distinct from the existing "Teacher" field (who performed/logged it). This reuses the existing `session_logs.coordinator_teacher_id` column rather than a separate one (a short-lived `assigned_by_teacher_id` column was tried and dropped the next day) — for this program type only, the field/dropdown is relabeled "Assigned by" — its option list briefly widened to every active teacher (2026-07-24) but was narrowed back to performance-coaches-only on 2026-07-28, same scoping as the regular Coordinator field everywhere else — so the value is already visible everywhere a session's Coordinator is shown (list view, CSV export, detail view) with no extra plumbing. Shown/relabeled in every panel that renders `SessionLogFormView.tsx`/`SessionLogDetailView.tsx` (admin and teacher/coach). Separately (no schema change), every user-facing "Fathom Summary" label across the session-log form/detail/list views — admin, teacher, and student panels alike — was renamed **"Fathom Transcript"**; the `fathom_summary` column/variable names are untouched. The per-session transcript `.docx` a student downloads from `/student/sessions` now also embeds the Fathom recording link when one was entered. As of 2026-07-24, **Topic, Video link (Fathom), and Fathom Transcript are all required** wherever the session-log form shows them (i.e. any non-no-show session; the latter two stay hidden — and so not required — for offline work). Also as of 2026-07-24, the "Download session log" CSV on a student's Details page (`StudentDetailView.tsx`'s per-invoice `handleDownloadInvoiceSessionLog`, admin `/admin/students/:id` and PC `/teacher/students/:id`) gained a **Fathom Link** column — `SessionLogDetailed` (`src/hooks/useInvoices.ts`) and both of its backing queries now also select `video_link`, which this CSV previously dropped entirely. See `db/docs/VERIFIED_DATABASE_STATE.md`.

### 2.3 Students & assignment
`students` (structured student records — **1 row live as of 2026-07-28** (`S1`, Batu Ozcelik), seeded after the full teacher/student/session purge described in §2.14 and §2.15; carries a nullable `user_id`, added 2026-07-02, for students who have a login), `pc_student_assignments` (which performance coach is currently assigned to which student; history-preserving — only one *active* assignment per student at a time via a partial unique index). As of 2026-07-29 a student also carries a **`status`** — `active` / `paused` ("On pause") / `completed` — set by their coach or an admin; **completing a student also ends their coach assignment**, which is why the status lives on `students` and not on the assignment row it outlives. It is written only through the SECURITY DEFINER `set_student_status()` function, since RLS cannot grant a coach one column and the completion path has to close an assignment row coaches otherwise cannot write. Every student is meant to have exactly one active coach at all times — enforced app-side (the new-student enrollment flow, see §2.9, requires picking a coach before it will submit) rather than a DB constraint; `db/scripts/backfill-pc-assignments.sql` brought all pre-existing students into compliance on 2026-07-01.

As of 2026-07-31 a student may **also** have a **College Counsellor (CC)** — `cc_student_assignments`, assigned by an admin from `/admin/cc-assignments`. A CC is a teacher flagged `is_college_counselor`, the same way a PC is one flagged `is_performance_coach`, and the two assignments are entirely independent: a PC is expected and permanent, a CC is optional and finite. That difference is why the CC table carries its **own `status`** (`active` / `completed`, deliberately no "on pause") while the PC table carries none — a counselling engagement ends while the student carries on with everything else, so the state can't live on `students.status` the way the coach engagement's does. Completing sets `unassigned_at` and **keeps the row**: the student drops off the counsellor's active list, but every session log written during the engagement stays exactly where it is and stays attributed to that counsellor, which is what the closed row is for. Completing the *student* closes any live CC engagement too. Writes go through the SECURITY DEFINER `set_cc_assignment_status()` so the status and `unassigned_at` can never drift apart; assignment itself is admin-only, mirroring the PC rule. A CC's session-log access is narrower than a PC's on purpose: they read **only the logs they wrote themselves**, not every session an assigned student had with other teachers (the broader policy shipped and was dropped the same day — see `20260806000200`).

**Assignment notifications** (2026-07-31): because assigning is admin-only, a coach or counsellor would otherwise only discover a change by noticing it on their My Students page — so the **`notify-assignment-change`** edge function emails *them* (not the student) whenever a student joins or leaves their roster. It fires on assign, on PC unassign, on a CC engagement being completed or reopened, on a CC assignment deleted as a mistake, and on the student being marked Completed (which closes both assignments at once, so both people are told). A reassignment sends two emails — the departing person first, then the new one — except when the "new" person is the one who already had them, which sends only the assign. Fire-and-forget via `src/lib/assignmentNotifier.ts`: the assignment write has already succeeded, so a slow or failed SMTP round trip never fails the assignment or blocks the admin. Which notifications a change implies is decided by `src/utils/assignmentNotifications.ts` (unit-tested); the function resolves the student and staff member from the assignment id itself, so a caller can't address mail at an arbitrary person, and skips silently when the staff member has no email or has been deactivated.

As of 2026-07-06, `students` also carries `graduation_year`/`birthday`/`school` (all nullable, alongside the pre-existing `phone_number`) — none required at admin add/renewal time, but gated as mandatory the moment the student first logs in via a full-screen "complete your profile" form (see §3.7 and `db/docs/VERIFIED_DATABASE_STATE.md`).

As of 2026-07-07 (student & parent dashboard merge), `students` also carries `notification_email` (the "send updates to" address — where invoices/notifications go, may match or differ from the login `email`, falls back to it when blank), `curriculum` (one of a small fixed set: IBDP / IB MYP / IGCSE / A Levels / AP / NA / National Curriculum / OTHER), an optional `report_card_url`, and `parent_phone_number` (the former parent/guardian's phone, now a plain field alongside the pre-existing `parent_full_name` rather than a linked `parents` row — that table, the `parent` role, and everything that depended on either were removed the same day; see §2.1/§2.9 and `db/docs/VERIFIED_DATABASE_STATE.md`'s changelog entry for the full mechanics, including the data purge that reduced `students` to its one remaining row).

### 2.4 Subject / curriculum catalogue
`program_types` (now hierarchical via `parent_id`), `course_types`, `subject_categories`, `curricula`, `curriculum_groups`, `subjects` (450 rows — all inactive rows were deleted 2026-07-02). Subjects/curricula can be submitted by teachers and carry `added_by_teacher_id` / `acknowledged_by_user_id` fields for admin sign-off — as of 2026-07-28, this no longer includes performance coaches, who lost their catalog-management UI (see §3.4).

Most curricula (IBDP, IGCSE, AP, etc.) organize subjects under groups (`subjects.curriculum_group_id` → `curriculum_groups`). `subjects.curriculum_id` (added 2026-07-01) exists for the opposite case — a curriculum with no group breakdown at all, letting a subject attach directly to the curriculum instead — and the session-log forms (and the teacher-subjects assignment flows) skip the group step entirely when that applies. As of 2026-07-02, **Standard Tests** uses exactly this shape: ACT, SAT, TOEFL, and IELTS (previously four separate standalone curricula) are now four plain subjects directly under the single "Standard Tests" curriculum — no groups, no group-selection step, just Curriculum → Subject → Add, same as it was for each of the four when they were their own curricula. When logging under one of these, the teacher/admin must explicitly pick the subject from the dropdown even if only one is assigned to them — it is never auto-selected/auto-logged without an explicit choice.

**Beyond Academic subjects** (Passion Projects, Career Exploration, Book Publishing, Finance and Literacy, Podcast, etc.) are picked as a single, completely flat Subject dropdown (`src/components/ui/BeyondAcademicSubjectSelect.tsx`) — no sections, no categories, not even an `<optgroup>`. As of 2026-07-02 (later), "Passion Projects" and "Career Exploration" are themselves plain `subjects` rows a teacher can pick directly, not category labels grouping other subjects — `subjects.category_id` is `NULL` for the whole Beyond Academic branch. See **[`db/docs/SUBJECT_HIERARCHY.md`](./db/docs/SUBJECT_HIERARCHY.md)** for the full hierarchy reference and the registry of every file that must change together whenever this hierarchy changes.

### 2.5 Packages, invoicing & reporting
`student_packages` + `package_topups` (purchased-hours tracking, auto-incremented via trigger), `invoices` + `invoice_line_items` + `invoice_packages` (with a `locked` status that blocks deletion), `monthly_reports` + five `monthly_report_*_stats` breakout tables (locking a report also freezes that month's `session_logs` from further edits), `zoom_invoices` (teacher-uploaded, one per teacher per month), `no_show_settings` (single-row, admin-editable teacher no-show payout rate — added 2026-07-04, see §2.2).

As of 2026-07-02, student reports (the generated invoice PDF, its on-screen expansion, and the admin Reports > Reports preview) are **sectioned by course type / bundle pool → program/subject → teacher** rather than by curriculum. `invoice_line_items` carries `student_package_id`/`course_type_id`/`program_type_id` so each line resolves to its pool and, when it has no subject, is labeled by its program name (College Counselling / College Essays, split as separate rows) instead of "—". The shared `aggregateReportSections`/`resolveReportSection` + `ReportSectionsView` (in `src/utils/buildInvoicePdf.ts` / `src/components/ui/ReportSectionsView.tsx`) render every report surface identically: **each section is its own self-contained table** (a navy header with the section name and its own total, a labeled Program/Subject · Sessions · Hours body, and indented teacher rows), with clear spacing between tables. A Foundation Program / All-In-One bundle gets a group header showing the combined total, then **one separate table per pool**. College Counselling shows as its own section/table. This same format is used by every downloadable student report — the per-invoice PDF, the whole-student "Download Report" on the Details tab, the on-screen expansions on the admin and teacher/PC pages, and the admin Reports preview. Line items are a snapshot, so these columns only populate on new generations — regenerate an old report to re-section it.

As of 2026-07-02, `student_packages` also supports **package-level locking** (`is_locked`/`locked_at`/`locked_by_user_id`/`locked_hours_used`), separate from monthly-report locking — an admin locks one specific package (e.g. once its hours are fully delivered) from `/admin/packages`, after which no more topups or linked `session_logs` changes are allowed against it, and the next renewal for that course type starts a brand-new package with no link back to the old one. See §2.9 and `db/README.md` for the full mechanism.

Also as of 2026-07-02, `student_packages` tracks **usage-threshold notifications** (`notified_50_pct_at`/`75`/`100`): the `notify-package-threshold` edge function fires after each non-no-show session save and emails the student's assigned Performance Coach the first time hours-used crosses 50%/75%/100% of the package total, then stamps the corresponding flag so it only fires once per threshold (a topup resets all three so they re-arm against the new total).

Also as of 2026-07-02, `student_packages.pool_label` lets a student have several concurrently-active pools of the *same* course type — e.g. a Foundation Program student gets a general Beyond Academic pool plus a labeled "Discovery Project" one. "Foundation Program" and "All-In-One" are real `course_types`, but only as a grouping label for a bundle of pools (`student_packages.package_type_id`) on `/admin/packages` and invoices — teachers still only ever see Academic / Beyond Academic / College Counselling in the session-log form, since a session's own `course_type_id` always comes from that pick, never from a bundle. Because a session's subject alone often can't say which of a student's several pools it belongs to, ambiguous sessions are saved unresolved (`session_logs.pool_ambiguous`) and the `notify-pool-issue` edge function emails the assigned PC to pick one from the "Pending Deduction" section — now available on both the admin student-detail page **and** a PC's own `/teacher/students/:id` (scoped to their assigned students); that choice is cached in the `session_log_pool_resolutions` table so the same teacher logging the same subject again auto-resolves without asking; resolving a session from "Pending Deduction" writes to this same cache — future sessions from that teacher on that subject follow the newly-picked pool too. One case needs no PC at all: if a session's subject name exactly matches one of the candidate pools' `pool_label` (e.g. subject "Career Exploration" vs. an All-In-One bundle's "Career Exploration" pool), `handle_session_log_package_lock()` resolves straight to that pool. As of 2026-07-03, the sticky resolution is checked **before** this subject-name match (not after, as originally implemented) — otherwise a PC manually reassigning a "Career Exploration" session elsewhere would have it silently snapped back on the next write, since the subject name would just re-match the same pool again. As of 2026-07-03 (later), the trigger also stops re-running resolution at all for a session that's already been deducted from a specific pool — so a later edit for an unrelated reason (fixing an hours typo, editing the date) can never silently drag that historical session onto a different pool. This split the old single `assignSessionToPool()` helper into `resolvePendingSession` (resolve a pending one), `updatePoolResolutionTarget` (change the assignment going forward, affecting only still-pending sessions), and `createPoolResolution` (set up a teacher/subject → pool assignment proactively, before any session has been logged — via a "+ Add assignment" form with Project/Teacher/Subject dropdowns in the renamed "Teacher/Subject → Project assignments" section on both the admin and PC student-detail pages). A fourth function, `reassignSingleSession` (move one already-resolved session to a different pool), existed briefly but was **removed 2026-07-04** — moving an already-logged session between pools is no longer possible from the UI at all, by design. The "Pending Deduction" queue and the pool-issue email both show the session's subject — falling back to its program name (e.g. "College Counselling") when it has no subject, rather than a bare "—". Full mechanism in `db/README.md`.

### 2.9 Student enrollment workflow (added 2026-07-02; single-login model since 2026-07-07; multi-package/multi-proof since 2026-07-25)
Students are no longer added purely by hand. `/admin/students/enroll` lets a coordinator submit an `enrollment_requests` row — either a brand-new student or a renewal against an existing student. **As of 2026-07-09, both flows collect only what's actually required, nothing else** — a real behavior change from the form's earlier, much longer "capture everything now" shape: **New Student** asks for just first name, student email (creates the login), and Performance Coach (all marked `*`); every other personal/contact field (last name, curriculum, phone, graduation year, birthday, school, report card, guardian name/phone/address/country) is intentionally not collected here at all — those are saved as `null` on the resulting `students` row and left for the student to fill in themselves via the mandatory first-login "complete your profile" gate (`StudentCompleteProfileGate.tsx`, see §3.7). **Renewal** is now purely "find the student, fill in package details" — the form shows only a read-only student search result (name/ID/email, with a "Change" link) and the Package section; none of the student's personal/contact info is shown or editable on this page anymore (the enrollment request snapshots it straight off the existing `students` row instead). Both flows share the same Package section — **as of 2026-07-25, a repeatable list** (course type, bundle-pool picker where relevant, preset/custom hours — each its own row, with "+ Add another package"/"Remove" controls) rather than a single package, so one admin can sell/renew several packages for one student in a single request instead of submitting one request per package; the whole request still has just one optional note. Submitting emails **one** invoice summary (every package listed, with a total once there's more than one) and a `/pay/:token` link (a public, login-free page — the token is the only access control) to the "send updates to" address, where they can upload one or more payment screenshots in a single submission — one file if paid all at once, several if paid in separate transactions (`enrollment_request_payment_proofs`, one row per file). An admin reviews it from `/admin/enrollments`: confirming creates, for a new student, a **single** login account (from the enroll form's Student email) plus every package on the request (`enrollment_request_packages`, resolved independently per line — a request can mix a standalone package and a bundle), and emails it its own credentials plus one combined package confirmation; a renewal tops up/starts a package per line respecting the locking rule above and emails one combined confirmation to the "send updates to" address and the student's own login email, deduped. Rejecting sends it back for re-upload with a reason. A request still `pending_payment` (nobody has uploaded proof yet) can be edited in place — contact/invoice metadata only, packages aren't editable inline — which resends the invoice with the corrected details — or deleted outright, from the Enrollments queue (`/admin/enrollments`, which defaults to showing every status rather than just "Awaiting Review"). Payment screenshots are stored in a private `payment-proofs` bucket (signed-URL access for admins only) — there's no pricing/amount field yet, the invoice lists package and student details only. The invoice email includes a matching PDF attachment (`buildEnrollmentInvoicePdf` in `src/utils/buildInvoicePdf.ts`, same header/footer branding as the other report PDFs, now a package table rather than a single row), generated client-side and passed to the edge function as base64 for attachment. Three edge functions drive this: `send-enrollment-invoice`, `submit-payment-proof` (the only edge function in this codebase with no JWT check — public by design), and `review-enrollment-payment`.

**2026-07-07 — student & parent dashboards merged, parent role removed.** There is no separate parent account/login/dashboard anymore — a student's own dashboard (§3.7) now covers everything the old `/parent/*` portal did, since a student and their guardian share the same information. The former parent/guardian's name and phone are kept as plain fields directly on the `students` row (`parent_full_name`/`parent_phone_number`) instead of a linked `parents` row, and the `user_role` enum no longer has a `parent` value. As part of this change, every student except `S1` (Divija Pandey) was deleted (she was migrated to the new single-record shape, her linked parent's name/phone/email copied onto her own row first) along with every `parents` row and every parent/deleted-student login — see `db/docs/VERIFIED_DATABASE_STATE.md`'s changelog entry for the exact mechanics.

As of 2026-07-02 this invoice → confirm/reject flow is the **only** way hours are added or packages created. The former direct-entry actions on the "Learner's actual hours" surfaces (the student-detail tab and `/admin/packages`) — "Add hours", "Add package type", "Sell package", and the bundle builder — have been removed so those views stay a consistent, read-only reflection of the same underlying balances (Lock/Unlock on `/admin/packages` is the one exception, since the locking rule above is what makes a renewal start a fresh generation). Renewal is exact: confirming a renewal tops up the student's existing *unlocked* package for that course type (24/24 with +10 → 24/34), or starts a brand-new package if the only prior one was locked.

The enroll course-type dropdown offers every active `course_types` row — the same list every other picker in the app sees — including the two "bundle" types, Foundation Program and All-In-One. Selecting one behaves differently depending on whether the selected (renewal) student already owns that bundle:
- **First-time purchase** (no unlocked pool of that bundle exists yet, or a `New Student` enrollment): the form previews the bundle's fixed set of labeled pools instead of a manual hours picker; the request records the bundle's name and total hours, and on confirm the edge function creates every pool at its own fixed hours. As of 2026-07-06, each pool's hours live in the **`bundle_pool_settings`** table (admin-editable only from the Admin Reports "Settings" tab — see §3) rather than a hardcoded `BUNDLE_POOL_DEFS` object that two files had to be kept in sync by hand.
- **Renewing a bundle already owned**: the form instead requires picking exactly *one* of the bundle's pools (`enrollment_requests.bundle_pool_label`) plus a manual hours amount (same preset/custom picker as a standalone package) — confirming adds hours to only that one pool, leaving the rest of the bundle untouched. This was a real bug before 2026-07-02: confirming any bundle renewal used to blindly re-create/top-up *every* pool in the bundle at its hardcoded default hours, even when the admin only meant to add hours to one that had run low.

Either way, the actual pool selected still follows the standard unlocked-tops-up / locked-starts-fresh rule (per pool, not per bundle) — picking a pool that happens to be locked starts a fresh one rather than erroring.

As of 2026-07-09, a Performance Coach can flag that one of their students needs a renewal without being able to process it themselves — `package_renewal_requests` (new table) + `/teacher/renewal-requests` (PC submits student + course type + optional suggested hours/label/note, which emails every active admin via the new `notify-renewal-request` edge function) + `/admin/renewal-requests` (admin acknowledges — a plain status flip, no email — then processes the actual renewal the normal way through `/admin/students/enroll`). `review-enrollment-payment` was extended so that confirming that renewal (or any package-creating confirm for the same student/course type) automatically flips any matching `pending`/`acknowledged` renewal request to **Renewed** and emails the requesting PC — the admin never has to remember to close the loop by hand. See `db/README.md`'s "Package renewal requests" section.

**As of 2026-07-16, `/teacher/renewal-requests`' form mirrors the same bundle/pool awareness `/admin/students/enroll` already has**, instead of always asking for a flat course type + hours regardless of what the student already owns: picking a bundle type (Foundation Program / All-In-One) that the selected student **already owns** (any unlocked pool with `package_type_id` = that bundle) now requires picking *which pool* needs renewing (a plain dropdown built from `bundle_pool_settings`, same as the admin form's "Pool to add hours to") before the existing hours picker; the chosen pool's name is folded into `package_size_label` so it shows on both the PC's and admin's queue. Picking a bundle type the student **doesn't already own** shows a read-only preview of the bundle's fixed pools/hours (informational only, same as a first-time purchase on the admin form) and asks for **no hours at all** — a first-time bundle request has nothing to guess at, since the admin form always creates the whole fixed bundle in one shot. `TeacherRenewalRequestsPage.tsx` fetches the selected student's existing packages (`useStudentPackages().fetchPackagesForStudent`) and the bundle pool defs (`useBundlePoolSettings`) to derive this, exactly like `AdminEnrollStudentPage.tsx`'s `derivePackageInfo`. No schema change.

### 2.10 Homework Generator (added 2026-07-08 — all 8 phases done)
Seven tables — `style_templates`, `content_uploads`, `generated_papers`, `question_bank`, `submissions`, `grades`, `session_insights` — let a teacher pick a student, a content source (that student's session-log Fathom summary, or an uploaded PDF — see note below), and a mix-and-match paper composition (e.g. 10× MCQ + 5× Short Answer questions), generate a paper via the **Gemini API**, review and publish it to the student's dashboard, have the student attempt it, and auto/AI-grade it on submit with a teacher-override pass. **As of 2026-07-14, the builder only offers the 5 simple/generic question types — Multiple Choice (MCQ), Fill in the Blanks, True/False, Short Answer, Long Answer — plus difficulty; it no longer asks the teacher to pick a curriculum/subject-specific template** (that machinery — the `style_templates` subject-hierarchy resolver, `AcademicSubjectPicker.tsx`, the IBDP/IGCSE/AP/etc. templates — still exists and still works for any paper already built with it, it's just not surfaced in the builder UI anymore; see `db/docs/HOMEWORK_GENERATOR_ARCHITECTURE.md`'s "Simplified builder" note). This is a from-scratch, multi-phase build. **Done so far:** Phase 1 (data layer), Phase 2 (the `style_templates` library — 12 exam-format rows), Phase 3 (the teacher **`/teacher/homework`** tab + composition builder), Phase 4 (the **`generate-homework-paper`** edge function — real Gemini generation, per-block structured output + retry, dedup against `question_bank`), Phase 5 (the **`/teacher/homework/:paperId`** review page — Answer-sheet / Student-view, inline editing, regenerate a question / block / whole paper, and **Confirm & Publish**), Phase 6 (the student **`/student/homework`** "My Homework" tab + attempt view — MCQ/fill-blank/subjective inputs, save progress, submit), Phase 7 (the **`grade-homework-submission`** edge function — MCQ/fill-blank auto-graded, subjective LLM-graded per mark-scheme point, plus one-click teacher mark override on the review page), and Phase 8 (PDF/DOCX export of either the Answer Sheet or the Question Sheet, via `src/utils/exportHomeworkPaper.ts` reusing the existing `jspdf`/`docx` tooling — teachers get both sheets, students only the question sheet). The edge functions require the `GEMINI_API_KEY` secret (objective grading still works without it; subjective grading degrades to "pending teacher review"). Upload-sourced generation supports **PDF only** — PPT/PPTX/DOCX text extraction isn't built yet and fails generation with a clear error. **Follow-up (2026-07-08):** an uploaded PDF is now auto-indexed into chapters/sections by the new **`index-content-upload`** edge function (Gemini extracts a chapter→section outline with page ranges into `content_uploads.outline`), so the teacher can scope generation to any combination of chapters/sections (`generated_papers.content_scope`) instead of the whole book; and the session-log content-source picker became a filterable list (subject / date-range / topic-search + full per-session detail). The feature is complete end-to-end and `GEMINI_API_KEY` is set — a live run just needs the current default branch deployed to the frontend. **Follow-up (2026-07-09):** publishing a paper now emails the student (the new **`notify-homework-published`** edge function, fire-and-forget from `useGeneratedPaper.publish()`) — sent to `students.notification_email`, falling back to `students.email`, with a direct link to the paper. **Follow-up (2026-07-09, later):** a student submitting now emails the paper-owning teacher (new **`notify-homework-submitted`** edge function). Grades are also gated behind an explicit teacher review now — AI/auto grading still runs immediately on submit, but `grades.published_at` (new column) must be set by the teacher clicking **"Publish grade to student"** on the review page before the student can see any marks at all (enforced by RLS, not just the UI — see `db/docs/VERIFIED_DATABASE_STATE.md`'s `grades` section); publishing a grade in turn emails the student (**`notify-homework-grade-published`**). Both the student's homework list and the teacher builder's "Your papers" list show a stable per-student serial (**"Homework 1, 2, 3…"** restarting at 1 for each student) and name each paper by its subject (`{subject} · Homework {N}`, via the shared `paperDisplayName()` helper as of 2026-07-14 — see below); the teacher list is additionally filtered by student. The teacher is asked for the subject wherever it isn't already known (upload-only generate, parse-a-past-paper, and reuse — a session log already carries it) — see the 2026-07-14 "Teacher builder UI cleanup" note in the architecture doc. **Follow-up (2026-07-09, later still):** the review page now has three always-available tabs — Question Sheet / Answer Sheet / Student's Answers — instead of the answer/question sheets disappearing once a paper is submitted; and the builder can **reuse an already-generated paper for a different student** (`content_source_type = 'cloned'`, new `generated_papers.cloned_from_paper_id`) instead of regenerating from scratch. **Post-deploy fix (2026-07-09):** generating with content source **"Both"** (session log + upload) was silently ignoring the session log and drawing only from the PDF — the per-block prompt never told Gemini a PDF was attached when a session log was also present. Fixed in `generate-homework-paper` (redeployed v18) — see the architecture doc's "Post-deploy fix" note. **Follow-up (2026-07-26) — parse an existing paper:** a teacher can now **upload a PDF, or one or more photos, of an existing paper** (the "Upload a past paper" tab on `/teacher/homework`) and have Gemini **transcribe its questions verbatim and build the answer key** (new **`parse-homework-paper`** edge function + a fifth `content_source_type`, `parsed`), instead of generating new questions. `content_uploads.file_type` was widened to accept image types for this. A multi-page paper can be photographed one page per photo and parsed as a single paper (2026-07-27 — the ordered `generated_papers.content_upload_ids`, one Gemini file part per page). After parsing it goes through the exact same review → publish → attempt → auto/AI-grade flow as any other paper (the questions_json shape is identical, so nothing downstream changed). **Follow-up (2026-07-14) — format preservation:** a transcribed question's `prompt` is now Markdown (a table on the original page becomes a real Markdown table, not run-together text) and Gemini crops out any genuine visual (pie chart, graph, diagram) it can't represent as text, storing it inline as `figures` on the question — the exact image from the uploaded paper, rendered everywhere (review, attempt, export) via the shared `QuestionContent` component. A multi-page PDF is now rasterized to page images client-side before upload (`src/utils/rasterizePdf.ts`, `pdfjs-dist`) so figures can be cropped from real pixels. See the architecture doc's "Parsed-paper format preservation" section. **Follow-up (2026-07-14, later still):** the student's "My Homework" list previously showed a bare "Homework #N" instead of naming the subject like the teacher list did — fixed by moving the naming format into the shared `paperDisplayName()` helper (`src/utils/homeworkGrading.ts`) both lists now call. Separately, the shared `StudentDetailView.tsx` behind `/admin/students/:id` and `/teacher/students/:id` (§3.2/§3.4) gained a fourth **Homework** tab, listing every paper published to that student with its stage and, once graded, its score — a PC's rows link to `/teacher/homework/:paperId`; admin's rows link to a read-only `/admin/homework/:paperId` view (added 2026-07-30). **Follow-up (2026-07-14, later still):** that tab's row-list (subject+number title, stage badge, score, optional link) was pulled out into a shared `HomeworkResultsList` component (`src/components/homework/HomeworkResultsList.tsx`, wraps `useStudentHomework`) once a second consumer needed the exact same thing: `/teacher/homework` now shows a PC-only **"A student's homework & results"** card (own `StudentSearch`, independent of the builder's own student picker) that looks up *any* student's full published homework + results right from the generator page, not just papers that PC built themselves. **Follow-up (2026-07-14, later still):** that card moved behind its own top-level tab — a PC now switches between **"Generate homework"** and **"Student results"** via an underline tab bar (same style as `StudentDetailView.tsx`'s Details/Learner's actual hours/Homework/Reports tabs) at the top of `/teacher/homework` instead of seeing both the card and the builder stacked at once; a plain teacher (no results card to begin with) sees no such tab bar. **Follow-up (2026-07-14, later still) — manual photo/PDF answer grading:** a student can now answer a subjective question with an **uploaded photo** instead of typing, or attach **one whole-paper PDF** covering every subjective question at once (objective mcq/true_false/fill_blank questions are unaffected either way) — **neither is ever AI-graded**; `grade-homework-submission` (redeployed v12) writes a pending placeholder and the teacher marks it by hand on the review page, clicking anywhere on the rendered image/PDF to drop a text comment (`AnnotatableMedia`, new shared component) the way margin notes work on a marked paper. New `submissions.whole_paper_answer` / `grades.whole_paper_grade` columns and a new private `homework-answers` storage bucket (student self-upload, mirroring `report-cards`). See the architecture doc's "Manual photo/PDF answer grading" section. Full design and phase status: **[`db/docs/HOMEWORK_GENERATOR_ARCHITECTURE.md`](./db/docs/HOMEWORK_GENERATOR_ARCHITECTURE.md)**. ### 2.11 Coordinator Logs (added 2026-07-29; redesigned 2026-07-15)
A Performance Coach files a periodic coaching check-in per student — **Type(s) of program** (fixed, read-only — auto-derived from the student's own packages, not a coordinator choice; see the 2026-07-16 note below), Primary Goal + Ideal Outcome + Goal Timeline, Progress Status, Biggest Challenge, Next Action, the subject/profile-building blocks the selected programs imply (see below), three Final Outcome fields (University Placement, Project Achievement, an Evidence Link for Profile Building) plus a per-Academic-subject **Current Grade** (versioned — each check-in records that subject's grade and the whole per-subject timeline of earlier grades is shown, in both the form and the read view; formerly labelled "Grade Improvement"), 9 ratings on one 0-5 scale all shown as **star pickers** (Student/Parent Engagement, Academic Progress, Referral Potential, Engagement/"how involved are the parents", Transformation/Outcomes, Loyalty/Retention, Referral/Advocacy, Parent Belief Score — the last 5 carry their scoring anchors as helper text; kept as separate fields even though some visibly overlap, per an explicit product decision not to merge them), an automatic **per-package Renewal** section (Renewal Status, Renewal Timing — one row per package, system-maintained, not entered in the form; see the automation note below), Referral Status, and a **Primary Relationship Owner** (fixed `Devi`/`PC/CC`/`Ascend Now (System)`) shown in the first section — fixed to `PC/CC` for a PC, admin-selectable. It's **admin + Performance Coach only** — a plain teacher and a student have no access at all, enforced by RLS, not just route/nav gating.

The form is **append-only, no edit** (as of the 2026-07-15 redesign): selecting a student prefills every field from their latest log so the PC edits forward from it, and any save writes a *new* row — there is no edit route or "Edit" button, and full history is kept for analysis. Opening the form from a student's **Coordinator Log** tab deep-links the student in (`…/coordinator-logs/new?student=<id>`) so it's pre-selected and prefilled. Which subject blocks appear is driven by the selected programs: **Academic** → Academic Subjects & Baseline Scores (the only block with baseline scores + Current Grades); **Beyond Academic / Foundation Program / All-In-One** → Profile Building Project (a flat Beyond Academic subject picker — the selected subjects *are* the project; no free-text field); **College Counselling / All-In-One** → College Counselling subjects (stored alongside the profile-building ones, no baseline).

Three tables: `coordinator_logs` (the check-in itself — repeating history, one row per check-in, same shape as `session_logs`, only `student_id`/`teacher_id`/`course_type_ids` (≥1 program) required), `coordinator_log_subjects` (child table pairing a subject with its baseline score and final-outcome grade, `ON DELETE CASCADE` — only Academic subjects carry a baseline/grade; the bucket is derived from the subjects catalogue), and `coordinator_log_options` (one shared table backing the 6 admin-editable dropdowns — Primary Goal, Progress Status, Biggest Challenge, Next Action, Renewal Status, Referral Status — discriminated by `list_key`, managed only from the Admin Reports **Settings** tab: add/rename/reorder/deactivate, plain text only, same "single admin-editable place" precedent as `no_show_settings`/`bundle_pool_settings`). "Type(s) of program/package" (fixed/derived `course_type_ids smallint[]`, see the 2026-07-16 note below) references `course_types` — the same list this app already calls "packages" elsewhere (enrollment, invoicing). `goal_timeline` is a month+year-only real `DATE` column (day always the 1st, CHECK-enforced) — the same "one real DATE column, derive month/year at display" convention as the rest of this schema (§4 Key Decision #1).

A PC is scoped to their own currently-assigned students via `pc_student_assignments` (mirrors `package_renewal_requests`/`student_packages`'s RLS shape, not `session_logs`' blanket-PC-read policy, since a PC must only reach their own assigned students here) — verified live via impersonation: a PC could insert/read a log for their own assigned student, while a plain non-PC teacher was rejected outright with an RLS violation on the identical insert. The subject picker reuses the same cascading Curriculum → Group → Subject(+Level) picker (Academic) / flat picker (Beyond Academic, College Counselling) as `TeacherSubjectEditor.tsx`, now split into the per-program blocks described above (Academic / Profile Building / College Counselling) shown by the log's selected Course Types. The shared `StudentDetailView.tsx` (`/admin/students/:id` and `/teacher/students/:id`) gained a 5th **"Coordinator Log"** tab showing the latest check-in's snapshot on top (so logging a new one for that student updates what's shown there) with every earlier entry kept linkable below it as history. See `db/docs/VERIFIED_DATABASE_STATE.md`'s "Coordinator Logs tables" section and `db/README.md`.

**Automatic per-package renewal, filed into the log (added 2026-07-15; Upsell Opportunity dropped and Upsell Timing renamed to Renewal Timing 2026-07-16).** Renewal Status and Renewal Timing are **not entered in the log form at all** — they're fully automatic and tracked **per package/pool** (a student can hold several packages, each at a different point in its lifecycle). Each coordinator log carries a set of per-package status rows (`coordinator_log_package_statuses`), snapshotted when the log is filed. When any package's status changes, the system **files a new coordinator log by itself** — today's date, everything else carried forward from the latest log (including `primary_relationship_owner`, which defaults to `pc_cc` when there's no prior log), attributed to the assigned PC — exactly like a PC filing an update. So the coordinator log's own append-only history *is* the dated record of what changed when. It fires off the same signals as the milestone emails: `student_packages.notified_75/100_pct_at` crossings plus `package_renewal_requests`. Per package: below 75% → *Not Due*; 75%+ → *Upcoming* (Renewal Timing = the month it crossed 75%); an open renewal request against that exact package (a standalone-course-type request only matches a standalone package of that type; a bundle-course-type request matches every pool in that bundle — so e.g. a "Beyond Academic" request never touches an All-In-One bundle's Beyond Academic pools) → *In Discussion*; a fulfilled one (pool since reset <75%) → *Renewed*; 100% with no renewal in motion → *Not Renewing*. **Referral Status is the only manual field** in this section (still on the form). The read-only per-package table is shown in the log detail view and on the student's Coordinator Log tab (`RenewalSection`). All DB-side — `sync_coordinator_log_for_student()` (append-on-change) + `trg_coordinator_logs_snapshot_statuses` (snapshot every log) + triggers on `student_packages` and `package_renewal_requests`; no edge-function changes. See `db/docs/VERIFIED_DATABASE_STATE.md`'s automation note.

**Fixed 2026-07-16 — a still-open request for a package the student doesn't have yet now shows up too.** The per-package loop above only ever iterated the student's *existing* `student_packages` rows, so a renewal request for a course type nothing currently matches (e.g. a standalone "Beyond Academic"/"College Counselling" request for a student whose only pools of those types live inside their All-In-One bundle, or a request for a bundle the student doesn't own at all) had no row to attach `in_discussion` to and silently never appeared anywhere in the coordinator log — this is exactly what happened to S1. `coordinator_log_package_status_rows()` now also emits a "phantom" row (`student_package_id = null`, no bundle/pool) per distinct course type among the student's still-open requests that don't match any existing package, always `in_discussion`. See `supabase/migrations/20260731000700_coordinator_log_phantom_package_requests.sql` and `db/docs/VERIFIED_DATABASE_STATE.md`.

**Changed 2026-07-16 — Type of program is no longer coordinator-editable.** "Type of program" used to be a `MultiSelectDropdown` the PC actively picked from (constrained to the programs the student had a package in, but still an active choice — including picking only a subset, e.g. logging just "Academic" for a student who also has a Beyond Academic pool). It's now a plain read-only display: `CoordinatorLogFormView.tsx`'s `courseTypeIds` is no longer form state a coordinator sets — it's derived directly from `studentProgramIds` (the same `student_packages` → program-id lookup the old picker's options were already constrained to), so a check-in always covers every program the student currently has a package in, exactly like the programs a student "has" are otherwise fixed facts, not something entered by hand. `course_type_ids` is still saved on submit and still drives which subject blocks (Academic / Profile Building / College Counselling) the form shows — only the picking mechanism changed. **No schema change** — `coordinator_logs.course_type_ids` stays `smallint[]`, since a student can still hold more than one program at once.

**Renamed to "Performance Coach Log" + two new fields (2026-07-16).** Every user-facing "Coordinator" label across the app was renamed **"Performance Coach"** — the session-log form/detail field (was "Coordinator (performance coach)"), the session-log list column + CSV header + "Coordinator/PC" filter, the analysis "PC / Coordinator" filter/table, the enrollment detail field, the exported invoice/session `.docx`/PDF labels, the student-detail "Coordinator" field, and the whole feature ("Coordinator's Log" → **"Performance Coach Log"** in the admin/PC nav, page titles, list, form, and the student-detail tab). Only the visible strings changed — routes (`/…/coordinator-logs`), DB columns (`coordinator_teacher_id`), table names (`coordinator_logs`), and code identifiers are unchanged. Two data changes shipped the same day: (1) `coordinator_log_subjects.baseline_score_date` — the date an academic subject's baseline was recorded, **auto-stamped as today** when the PC adds the subject (not entered by hand) and shown inline in brackets next to the baseline (e.g. `5 (16 Jul 2026)`) in the form and every read view, carried forward on prefill so it keeps its original date; (2) `coordinator_logs.is_automated` — distinguishes the automatic per-package renewal snapshots from logs a PC actually filed by hand, so the student's Performance Coach Log tab now shows **"First logged by Performance Coach — <date>"** (the earliest `is_automated = false` log's date, "not yet" if none). `sync_coordinator_log_for_student` stamps `is_automated = true` and carries `baseline_score_date` forward; existing rows were backfilled by content heuristic. See `supabase/migrations/20260731000900_coordinator_log_subject_baseline_date.sql` / `20260731001000_coordinator_log_is_automated.sql` and `db/docs/VERIFIED_DATABASE_STATE.md`.

### 2.12 Subject Notes (added 2026-07-17)
One table — `subject_notes` — lets a teacher or performance coach file a **named note** against a student + subject: a short written body and/or an uploaded file **in any format** (PDF, DOCX, image, …). The teacher-facing flow is `/teacher/notes` (§3.4) — search a student, pick a program branch (Academic / Beyond Academic / College Counselling), pick a subject, then add the note. For a **plain teacher** the subject list is the subjects **that teacher has actually taught that student** (derived from the teacher's own `session_logs` for the student — the same "a subject appears once it's been taught" rule the student Overview uses). For a **performance coach** (as of 2026-07-21) it's **every** subject the student has sessions in, since a coach coordinates rather than personally teaches, so is logged as the session's *coordinator*, not its `teacher_id`; scoping to their own id would leave the list empty (RLS already lets a coach read all of a student's session logs and manage all notes). A note is keyed by `subject_id` + `curriculum_id` (nullable, set for Academic subjects) — the **same key the student Overview tab drills into** — so the student sees it under the matching subject on `/student/overview` alongside that subject's session logs (§3.7). Files live in the private `subject-notes` storage bucket (path `<student_id>/<uuid>.<ext>`), accessed via short-lived signed URLs. RLS: admins manage all, a teacher manages only their own notes (`teacher_id = my_teacher_id()`), a performance coach manages all (`is_performance_coach()`), and a student reads only their own (`can_view_student(student_id)`); the bucket mirrors this (staff upload scoped to a real student-id folder, student reads only their own folder). No edge function — direct table + storage writes. The `/teacher/notes` add-note widget is the shared `src/components/notes/AddSubjectNoteForm.tsx` (self-contained: uploads the file, if any, then inserts the `subject_notes` row on its own "Add note" button). The **session-log form** (`SessionLogFormView.tsx`, admin + teacher) has its own inline version of the same fields — once a student and a subject are picked, an "Add a note for this subject" block (Note name / Note / Attachment) appears; there is **no separate button** and the note name is optional. The note is saved automatically as part of **Log session**: on submit, once the session row is saved, if the note has any content (a body or a file) `handleSubmit` uploads the file (if any) and inserts a `subject_notes` row (title falling back to the topic, then "Note"). It's **never stored on or shown with the session log** — the `session_logs` payload is unchanged; the note only ever lands in `subject_notes` (best-effort, so a note failure never undoes the saved session). See `db/docs/VERIFIED_DATABASE_STATE.md`'s "subject_notes" section.

### 2.18 College Counsellors become peers of Performance Coaches (2026-08-03)
The College Counsellor role shipped (§ the 2026-07-31 entries) as a deliberately narrow one: log your own sessions, see your own roster, nothing else. That is **reversed** — a CC now sees and does everything a PC does, including filing package renewal requests.

Rather than adding a second, near-identical policy beside every `is_performance_coach()` one, all **32** of them were rewritten in place (**same policy names**, so existing references stay valid) on top of two new SQL helpers: **`is_coach_or_counselor()`** (the PC-or-CC role test) and **`is_my_assigned_student(student_id)`** (a live assignment in **either** `pc_student_assignments` or `cc_student_assignments`). 1. **The CC sidebar is now the coordinator sidebar** — General / a role-named section (My Students, Students' Logs, the coordinator log) / renewal requests / My Profile. ### 2.6 Row Level Security (RLS)
RLS is **enabled on all 46 tables** (45 + `pc_profiles`, added 2026-07-18). The general pattern: `is_admin()` grants full access everywhere; teachers/coaches/counsellors get access scoped through `my_teacher_id()`, `is_coach_or_counselor()`, or `is_my_assigned_student()` (either assignment table — see §2.18; before 2026-08-03 these were `is_performance_coach()` and a direct `pc_student_assignments` join). Some tables carry duplicate/overlapping policies left over from iterative migrations (functionally redundant, not broken) — see the live-state doc for specifics. As of 2026-07-05, `students` (previously the one table with unscoped `true` SELECT/INSERT/UPDATE policies for any authenticated user — a real gap, not just a duplication issue) now follows the standard pattern too: admin gets `ALL`, any staff member (a `teachers` row) can `SELECT` every student, a student can `SELECT` only their own record via `can_view_student()`, and only admin can write at all. Also as of 2026-07-05, `curricula` and `subjects` no longer carry the over-broad "any authenticated user can insert" policy (which had let non-staff roles inject catalogue rows) — curricula inserts are now coach/admin only, and subject inserts are scoped to any user with a `teachers` row (so a plain teacher's `/teacher/subjects` self-service still works, non-staff roles are blocked). A full DB-vs-frontend gate audit on the same date confirmed the apparent `users`/`teachers` self-update privilege-escalation path is blocked by the `prevent_self_privilege_escalation` trigger (verified live). As of 2026-07-07, `can_view_student()` lost its parent-lookup branch (there's no parent role to check anymore) — a student can only ever see their own record. See `db/docs/VERIFIED_DATABASE_STATE.md` for the live-verified policy set and the audit write-up.

**Important infrastructure note:** RLS policies only work if base table `GRANT`s also exist for the `authenticated`/`anon` roles — a bug we hit once already (policies correct, but zero base grants meant every request was blocked before RLS was even evaluated). Worth re-checking whenever a "policy looks right but still gets denied" situation comes up.

### 2.7 Helper functions & triggers (highlights)
- **`is_admin()` / `is_performance_coach()` / `my_teacher_id()`** — used throughout RLS policies.
- **`get_email_for_username(username)`** — resolves username → the account's **Auth login email** (`auth.users.email`) for the login flow, before authentication. As of 2026-07-05 it reads `auth.users.email` (not the mutable `public.users.email`) so an in-app email change can never desync the resolver from what Auth authenticates against — the bug that once locked a coach out (see `db/docs/VERIFIED_DATABASE_STATE.md`).
- **`create_teacher_profile()` / `create_admin_profile()` / `create_user_profile()`** — provisioning helpers; the last one auto-fires on every new `auth.users` row.
- **`sync_teacher_pc_role()`** — keeps `users.role` in sync whenever a teacher's `is_performance_coach` flag changes.
- **Locking triggers** — block edits/deletes on locked invoices, locked monthly reports, their stats breakouts, and session logs that fall inside a locked reporting month.

### 2.8 Migration history — consolidated
This repo used to have two overlapping, out-of-sync migration systems (`db/schema/*.sql`, 28 numbered files, and 35 ad-hoc-applied timestamped files in `supabase/migrations/`, whose own tracking table was empty). Both have been deleted and replaced with a single consolidated migration — **`supabase/migrations/20260701000000_baseline_full_schema.sql`** — generated directly from live introspection of the database, reproducing the full schema exactly (tables, constraints, RLS policies, functions, triggers, grants, storage buckets). Full details in `db/docs/VERIFIED_DATABASE_STATE.md` under "Why this file exists." **`supabase/migrations/` is now the single migration system going forward** — add new changes there as new timestamped files, applied via tracked `supabase db push`, so the migration-history table stays accurate this time.

### 3.4 Teacher / Performance Coach dashboard (`/teacher/...`)
A performance coach uses mostly the same dashboard as a teacher (same profile/subjects/sessions/invoices/hours/settings routes), plus coach-only routes for managing their assigned students. A **college counsellor** shares the same shell. From 2026-07-31 to 2026-08-03 their sidebar was deliberately narrow (Session Logging, My Students, My Profile, nothing else); **as of 2026-08-03 a CC sees everything a PC does** — same sectioned sidebar, same routes, and they can file renewal requests — backed by the RLS widening in `20260808000000_cc_gets_pc_access.sql` (§2.18). Only two things differ by role: the section is named after whichever hat they wear (`staffRoleLabel`), and **My Students** points at `/teacher/cc-students` for a counsellor and `/teacher/students` for a coach (`myStudentsPath`). A teacher may carry both flags even though `users.role` holds only one login role; in that case `TeacherLayout.tsx` labels the section "Performance Coach", links My Students to the PC roster, and adds **My CC Students** as an extra entry — and the CC grants still apply because the `is_college_counselor()` RLS helper reads the `teachers` flag rather than `users.role`. The login role itself is kept in step with the flags by the `sync_teacher_staff_role()` trigger (PC → CC → teacher precedence, matching `loginRoleForStaff()`); its PC-only predecessor was silently resetting every counsellor to `teacher`, which bounced them out of their own routes and made the sidebar flip shape after each navigation. `useMyTeacherProfile` also caches the teachers row per user, since every page mounts its own `TeacherLayout` and refetching from scratch each time made the sidebar visibly settle one render late. As of 2026-07-26, a PC's sidebar (`TeacherLayout.tsx`) is grouped into collapsible sections like the admin one: a **General** group holding the tabs shared with plain teachers (Session Logging, Homework Generator, My Hours, My Subjects, Notes), a role-named group holding the coordinator tabs (My Students, Students' Logs, the coordinator log), then **PC & CC Renewal Requests** and **My Profile** standalone at the bottom — renewal requests moved out of the role group on 2026-08-03, since both roles file them. A plain teacher's sidebar stays a flat list (no grouping). As part of the same change, the coach's "My Students' Session Logs" view — previously a second horizontal sub-tab on `/teacher/sessions` — moved to its own `/teacher/student-logs` route (`TeacherStudentLogsPage.tsx`) so it can sit in the Performance Coach group; `/teacher/sessions` now shows only the coach's/teacher's own sessions. As of 2026-07-28, a PC no longer has any subjects-*catalog* route — `/teacher/subjects-library` (`CoachSubjectsManagePage.tsx`) was removed since PCs are no longer allowed to add subjects to the shared catalog; the catalog is now admin-only, managed exclusively from `/admin/subjects`. A PC's own `/teacher/subjects` ("My Subjects" — self-service assign/remove of already-existing subjects, not catalog creation) is unaffected.

Added 2026-07-09 — a mandatory first-login gate mirroring the student one (§3.7): admin's add-teacher form only requires `first_name`, leaving `last_name`/`email`/`phone_number`/`country` optional, so `TeacherLayout.tsx` checks `teacherNeedsProfileCompletion()` (`src/utils/profileCompletion.ts`) on every teacher route and, if any of those four are still missing, shows `TeacherCompleteProfileGate.tsx` full-screen instead of the dashboard until they're filled in. ### 3.6 Security model (client-side)
`ProtectedRoute` checks role before rendering a page and redirects mismatches to the correct dashboard. **This is a UX convenience only** — the real security boundary is RLS on the database itself. Client-side checks can be bypassed; RLS cannot.

## 4. Key Decisions Made Along the Way

These are the resolved questions that shaped the schema — recorded here so the reasoning isn't lost:

1. **Date storage**: one real `DATE` column, never split into separate year/month/day fields (avoids drift/redundancy). Month/year are derived via query when needed.
2. **Session duration**: must round to 15-minute (0.25 hr) increments — enforced by a CHECK constraint as a safety net, regardless of how the value gets entered.
3. **Session number grouping**: superseded — `session_no` was ultimately **dropped from the schema entirely** rather than automated. No running-count column exists anymore.
4. **Coordinator = Performance Coach**, not a separate identity. Performance coaches are teachers with an `is_performance_coach` flag — not their own table, since admin never overlaps with teacher/coach but coaches always are teachers.
5. **No public signup** — every account is admin-created. The `create_user_profile` trigger fires automatically regardless of *how* the `auth.users` row was created (Admin API, Dashboard, or script).
6. **Username-based login**, but Supabase Auth still does all real password hashing/verification — we never built or stored our own password logic.
7. **Subjects**: moved off plain free text — a structured `subjects`/`curricula`/`subject_categories` catalogue now exists, seeded from the company's real subject list (450 active subjects), with teachers/coaches able to submit new ones pending admin acknowledgement.
8. **Student records**: moved off plain free text — a structured `students` table now exists, with `session_logs.student_id` as the FK. The old free-text name columns remain (nullable) for backward compatibility.

### Known gaps in the build
- **In-app account creation now covers admin, teacher, and student roles.** The `create-teacher-with-user` Edge Function covers admin-created teacher accounts, `create-admin-with-user` covers admin accounts (the `/admin/admins` tab, added 2026-07-17 — see §3.2), and `review-enrollment-payment` covers the student account created via the enrollment workflow (§2.9), which has its own read-only dashboard (§3.7). Every role that exists (`admin` / `teacher` / `performance_coach` / `student`) now has an in-app creation path — a performance coach is just a teacher with `is_performance_coach = true`, created from the same add-teacher form.
- **No pricing/amount field on the enrollment invoice yet** (§2.9) — the emailed invoice lists package/hours/student details only, since no price/currency concept exists anywhere in this schema. Add a price (manual entry or a price list) when billing amounts are needed on the invoice.
- **A first-time bundle purchase (Foundation Program / All-In-One) still uses fixed pool sizes, not editable per-sale.** `review-enrollment-payment` creates each pool from the hardcoded `BUNDLE_POOL_DEFS` hours the first time a student buys the bundle. Renewing a bundle already owned *is* now editable per-pool (pick one pool + a manual hours amount, added 2026-07-02) — only the initial "create the whole bundle" step is still fixed. If the initial mix ever needs to vary per sale, the request would need to carry per-pool hours instead of just a course_type_id + total.
- **Duplicate/redundant RLS policies** exist on several tables (`session_logs`, `curricula`, `subjects`, `subject_categories`, `teacher_subjects`, `program_types`) — leftovers from iterative migrations, not currently broken, but worth consolidating.
- **`AdminEnrollmentsPage.tsx`'s pending-payment edit modal doesn't have a `student_phone_number`/graduation-year/birthday/school/report-card field**, even though `updateEnrollmentRequest`'s input type supports most of them — it only edits the original, smaller field set (as of 2026-07-07 it does have first/student/notification email and curriculum). Low-impact since it's a quick pre-payment typo fix, not the primary intake form (`AdminEnrollStudentPage.tsx`, which does have all of these), but worth extending for consistency.

### Infrastructure lessons learned (for future reference)
- When granting database access to new roles, **always verify base table GRANTs exist**, not just RLS policies — RLS filters rows on top of grants, it doesn't replace them.
- Triggers on Supabase-managed schemas (like `auth.users`) can't be toggled via plain `ALTER TABLE ... ENABLE TRIGGER` from the SQL Editor (ownership restriction) — recreating the trigger from scratch (`DROP` + `CREATE`) works without needing elevated ownership.
- **Before writing a new migration, verify current live schema directly** (Supabase MCP `list_tables`/`execute_sql`, or the Supabase Dashboard) rather than assuming `supabase/migrations/*.sql` alone is current — it's the single source of truth going forward (see §2.8), but only stays that way if every future change actually goes through it via tracked `supabase db push`.
