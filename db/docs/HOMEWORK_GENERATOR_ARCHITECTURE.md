**Updated 2026-07-16 (usability follow-up, five fixes — frontend-only, no schema/edge-function change):**
1. **Stable homework numbering.** `assignHomeworkNumbers` (`src/utils/homeworkGrading.ts`) now numbers a student's papers by **`created_at` uniformly** instead of "published papers first (by `published_at`), drafts appended after". The old scheme renumbered a paper the moment it was published (a draft numbered #6 among several drafts jumped to #4 as it left the drafts-at-the-end bucket). `created_at` is immutable, so a paper keeps the same "Homework N" for its whole life. Trade-off: a student's list may skip a number that's still a draft on the teacher side (RLS hides drafts); the gap fills in on publish.
2. **Whole-paper answer accepts a PDF and/or photos, multiple files.** `submissions.whole_paper_answer` (jsonb, no migration) gained an optional `files: {file_url, file_name}[]` array; `file_url`/`file_name` still hold the first file for back-compat and the grading edge function's truthy presence-check (so `grade-homework-submission` was **not** changed). New `WholePaperAnswer` type + `wholePaperAnswerFiles()` helper (`src/types/database.ts`). `StudentHomeworkAttemptPage`'s upload input now accepts `application/pdf,.pdf,image/*` + `multiple` and appends files. `resolveWholePaperImages()` (`homeworkAnswerMedia.ts`, replacing `resolveWholePaperPageImages`) resolves each file to images (PDF → pages, photo → itself) flattened in file order, so teacher and student index annotations (`page` = flat slot) identically.
3. **Teacher list shows "Needs review", not "Graded", until the grade is published.** `generated_papers.status` flips to `graded` the instant AI grading runs on submit; the teacher's "Your papers" list read that as final. New `teacherPaperStage()` + `TEACHER_STAGE_*` (`homeworkGrading.ts`) report `needs_review` for any submitted paper whose `grades.published_at` is null. `useGeneratedPapers` now also fetches each paper's submission + grade to drive this.
4. **AnnotatableMedia sizing rework — the page/photo no longer gets cut, and is easily resizable.** The old layout rendered the page at the full reading width AND appended the comment margin, forcing a horizontal scroll that hid the page's left edge whenever you scrolled right to reach the comments. It now MEASURES the available width (ResizeObserver) and fits the page within it after reserving the margin, so page + comments always fit together at the default ("Fit") size; a drag slider + −/+ buttons zoom 50–300%. `maxWidthClass?: string` prop replaced by `readingWidthPx?: number`.
5. **Students see their answers + the teacher's comments anchored, like the teacher added them.** The student's whole-paper view and per-question photo view (`QuestionAttemptCard`) now pass `readingWidthPx`, so once a grade is published they get the same Google-Docs-style anchored comment margin the teacher used (falling back to a list beneath the image on narrow widths).

**Updated 2026-07-16 (second usability follow-up, six fixes — frontend-only, no schema/edge-function change):**
1. **Per-question photo answers now also accept a PDF, not just images.** `QuestionAttemptCard`'s upload input changed from `accept="image/*"` (with `capture="environment"`) to `accept="application/pdf,.pdf,image/*"` (capture dropped, matching the whole-paper input's own pattern) — a student can now attach a PDF of hand-worked answers to a single question, same as they always could for the whole paper. `homeworkAnswerMedia.ts`'s `resolveAnswerFileImages`/flatten logic (previously whole-paper-only) was generalized into an exported `resolveAnswerImages(files)`, and both `QuestionAttemptCard` and `TeacherQuestionPhotoReviewPage` now call it instead of the old image-only `resolvePhotoAnswerUrls` (removed). No `Annotation`/`PhotoAnswer` shape change: `file_index` already just indexes into whatever `images` array `AnnotatableMedia` is given, so a PDF's rasterized pages slot in exactly like extra photos would — old annotations on image-only answers resolve identically since that array was always 1:1 with `files` in that case. UI copy updated accordingly ("Upload photo or PDF", "Photo/PDF answer", etc.).
2. **Publish removed from the two annotation sub-routes entirely** (`TeacherWholePaperReviewPage`, `TeacherQuestionPhotoReviewPage`). First cut (same day, superseded within hours) tried hiding "Publish grade to student" only while a comment was actively being drafted (`AnnotatableMedia` gained an `onDraftOpenChange` prop for this) — but publishing is a whole-*submission* action while each of these routes only ever covers one attachment/question, so the button reappeared the instant a comment was saved and teacher feedback said it still felt like it was "on the annotation page." Fixed by removing the Publish button (and `handlePublish`/`publishing` state/`publishGrade` destructure) from both routes outright, replacing it with a plain link back to the paper's Student's Answers tab ("Publish this grade from the paper's Student's Answers tab once you're done reviewing") where `TeacherPaperResults`'s own existing Publish button still lives — so publishing only ever happens once every question's mark has actually been reviewed together, not piecemeal per annotation sub-page. `onDraftOpenChange` was removed from `AnnotatableMedia` again since nothing consumes it anymore (it had no other caller).
3. **Trackpad pinch-to-zoom on `AnnotatableMedia`.** The existing slider/±buttons zoom is unchanged, but the component now also listens for `wheel` events with `ctrlKey` set (how browsers report a two-finger trackpad pinch, absent a standard cross-browser pinch event) via a native, non-passive listener on the wrapping container — React's own `onWheel` is passive by default and can't call `preventDefault()`, which pinch-zoom needs to stop the browser's own page-zoom. A plain two-finger scroll (no `ctrlKey`) is left untouched. A `title` tooltip on the size control documents the gesture.
4. **`TeacherPaperResults` ("Student's Answers" tab) spacing pass.** This was the most visually dense screen in the feature (score banner, actions, whole-paper link, and every question packed at `gap-3`/`p-4`/`mt-2`). Widened to `gap-4`/`p-5` between and inside question cards, `mb-6`/`mb-5` around the score banner and whole-paper link, and `mt-3` between each question's prompt/answer/feedback blocks — matching the roomier spacing already used on the Question Sheet/Answer Sheet tabs (`TeacherHomeworkReviewPage`'s `gap-5`/`p-5` cards). No layout/behavior change, spacing only.
5. **"Generate a paper" / "Upload a past paper" tab row scrolls horizontally instead of wrapping.** `TeacherHomeworkPage`'s tab pill row gained `overflow-x-auto whitespace-nowrap` (and each button `shrink-0 whitespace-nowrap`), so a narrow viewport scrolls the row sideways rather than wrapping the second tab onto its own line or squeezing both labels.
6. **Question/Answer sheet PDF/Word export collapsed to a dropdown.** `HomeworkExportButtons` used to render, per offered sheet, a pill with the sheet name plus a PDF button and a Word button inline — two sheets (the teacher's Question Sheet + Answer Sheet) ate most of the page header's width. Each sheet is now a single "{Sheet name} ▾" button that opens a small "Download as PDF"/"Download as Word" menu (click-outside-to-close, no new dependency — same lightweight pattern as `RowMenu`, just not portal-rendered since this isn't nested inside a clipping ancestor). Same `exportHomeworkPaperPdf`/`exportHomeworkPaperDocx` calls underneath; purely a layout change.

**Updated 2026-07-16 (third usability follow-up) — `AnnotatableMedia` gets a second, left-hand comment margin.** A teacher reported that a pin dropped on the left half of a page still got its comment card in the (only) right margin, far from the pin it belonged to, and that the right margin got crowded once several pins were scattered across a page. `AnnotatableMedia` now offers a second margin on the left: a pin/draft with `x < 50` renders its card there instead of the right margin, split via a new `needsLeftMargin`/`showLeftMargin` (mirrors the existing `showMargin` gating — measured `containerW`, but requiring room for a *second* margin: `DOUBLE_MARGIN_MIN_CONTAINER_PX = MARGIN_MIN_CONTAINER_PX + MARGIN_WIDTH_PX + GAP_PX`). Deliberately lazy: the left margin only appears once there's an actual left-side pin/draft to show (`needsLeftMargin`), so a page where every comment happens to be on the right — the common case — reserves no extra width and renders exactly as before. `pageWidthPx`/`rowWidthPx` sizing was generalized from "reserve one margin" to "reserve `marginsWidthPx` (right, plus left when shown)". No prop change — every existing consumer (whole-paper PDF, per-question photo/PDF, student read-only view) picks this up automatically since they all render through this one component.

**Updated 2026-07-16 (fourth usability follow-up) — fixed: a graded per-question photo/PDF answer showed an empty "Write your answer" box instead of the image + teacher comments on the student's own attempt page.** Root cause in `QuestionAttemptCard.tsx`: `mode` (`"write" | "photo"`) was `useState`-initialized from `isPhotoAnswer(answer)`, but `answer` is still `null` on the component's very first render — `StudentHomeworkAttemptPage` starts `answers` at `{}` and only hydrates it from the loaded submission in an effect that fires *after* that first render/mount. A `useState` initializer only runs once, so `mode` got permanently stuck at `"write"` the instant the real (possibly photo/PDF) answer arrived a moment later, regardless of what the answer actually was — reproducible on any already-graded photo/PDF-answered question, and equally on a still-in-progress paper if the student left and resumed a draft that already had a photo attached. Fixed by deriving `effectiveMode = photoAnswer ? "photo" : mode` and using that (instead of raw `mode`) everywhere the component decides what to render — safe because switching to "write" always clears the answer via `onChange(null)`, so a truthy `photoAnswer` and `mode === "write"` can never legitimately coexist; whenever there's an actual saved photo/PDF answer it's always shown, and `mode` only matters for the "toggled to photo but haven't uploaded yet" in-between state. Same root-cause class as the `contentKey`/`resetForKey` pattern already documented on `AnnotatableMedia` (state initialized from a prop that arrives after mount) — this is the same fix shape, just via an always-recomputed derived value instead of a reset-during-render comparison, since there's no "previous key" to compare against here (just "does a real answer exist right now").

**Updated 2026-07-16 (fifth usability follow-up) — math-curriculum questions render as actual formulas instead of raw LaTeX text.** A teacher reported an IB Math HL paper showing literal `$f(x) = \frac{4x^3}{3} - 16x$`-style text in the question sheet — `QuestionContent.tsx` (`react-markdown` + `remark-gfm`/`remark-breaks`) had no math-rendering support at all, so a math paper's generated LaTeX (Gemini's default output style for this content, with no notation instruction from this app's prompts) just showed as backslashes and dollar signs. Added `remark-math` + `rehype-katex` + `katex` (new dependencies, `katex/dist/katex.min.css` imported once in `QuestionContent.tsx`) to both `ReactMarkdown` call sites (`QuestionMarkdown` and the per-row renderer inside `LineNumberedMarkdown`).

**The one real complication, verified directly rather than assumed:** this app also generates business-studies papers whose passages are full of bare currency like *"...was $3.5 billion and is forecast to grow to $4 billion by 2027."* — remark-math treats any `$...$` pair as math with no regard for content, and a live test confirmed it pairs those two dollar signs and renders the entire sentence between them as garbled math glyphs (initially assumed remark-math's boundary rule — no whitespace touching the delimiters — would protect against this; a direct test proved that assumption wrong before it shipped). Fixed with a new `src/utils/remarkMathGuard.ts`: a remark plugin, run immediately after `remarkMath`, that walks the parsed tree and reverts any math node back to plain text (reconstructing the original `$...$`/`$$...$$`) unless its content actually looks like LaTeX — has a backslash command (`\frac`, `\in`, `\mathbb`, ...), or contains no ordinary English word (4+ lowercase letters in a row). Verified against the *real* stored content for both papers (via `execute_sql`, not paraphrased test strings): every one of 34 genuine math spans across three real IB Math HL question prompts rendered correctly, and the real Business Management passage (10+ dollar amounts: "$100 000", "$250 million", "$3.5 billion", etc.) produced **zero** false-positive math spans. `rehypeKatex` is configured with `throwOnError: false, strict: false` as a second safety net for a span that passes the look-like-math check but isn't valid TeX (e.g. a tight "$50-$75" price range with no surrounding words) — renders a visible inline KaTeX error instead of throwing and blanking the page. New user-facing dependencies noted in `README.md` §1.

**Follow-up the same day: the first pass only fixed a question's own prompt text.** A teacher immediately reported the mark scheme ("Find the derivative $f'(x)$.") on the Answer Sheet still showing raw LaTeX — `QuestionMarkdown` was only wired into `QuestionContent`/`StimulusContent` (prompt + stimulus text), while every OTHER place Gemini-generated text is displayed used a plain `<span>`/`<p>`/template string instead: `QuestionReviewCard.tsx`'s mark scheme points, MCQ/true-false options, and fill-blank answer key; `TeacherPaperResults.tsx`'s AI feedback (`qg.feedback`), per-point breakdown, and the student's echoed MCQ answer choice; `QuestionAttemptCard.tsx`'s AI feedback, per-point breakdown, and its own MCQ option list. All of these can equally contain Gemini-generated LaTeX (a mark scheme point, an MCQ option, or a grading comment on a math question), so all of them were switched to render through `QuestionMarkdown` too. `QuestionMarkdown` gained an optional `className` prop (default unchanged: `"text-sm text-navy-700"`) so it can be dropped into a differently-sized/colored context (a muted `text-xs` per-point line, an inline MCQ option) without fighting its own default prose styling — the caller's className now fully controls that. A couple of call sites (`QuestionReviewCard`'s fill-blank answer, `TeacherPaperResults`' `StudentAnswer` MCQ echo) had their wrapping element changed from `<p>` to `<div>` since `QuestionMarkdown` always renders a block-level `<div>` internally (a `<div>` inside a `<p>` is invalid HTML and trips React's dev-mode nesting warning). The one deliberately-unchanged spot: `QuestionReviewCard`'s mark-scheme-point **edit** `<input>` still shows the raw LaTeX source while editing, which is correct — a teacher editing needs the actual text, not its rendered form.

**Deployment note (important):** there is no CI that deploys the edge functions or applies migrations — both are done out-of-band via the Supabase MCP connection / `supabase` CLI. The Vercel frontend deploys from the repo on push to the default branch. If the live site behaves like an older phase (e.g. generation writes a *placeholder* paper and the `generate-homework-paper` function shows no invocation in its logs, or the student has no "My Homework" tab), the cause is a **stale frontend deploy**, not missing code — the fix is to deploy the current default branch, not to rebuild the feature.

This is a from-scratch feature: nothing under this name existed in the codebase before 2026-07-08 (the only prior "homework" reference was an unrelated `program_types`/topic label in the session-log form). The full design was too large to build in one pass, so it's split into phases that can each be picked up independently by a future session. Each phase below states its goal, what it touches, and its done-state.

## The workflow this is building toward

```
Teacher opens Homework Generator tab -> picks the student -> sees that student's session logs
        -> picks content source: Session Log (Fathom transcript/summary) or Upload (PDF only as of Phase 4; PPT/DOCX pending)
        -> picks paper composition: mix-and-match question blocks by curriculum/style
           (e.g. 4x IBDP Section A + 5x MCQ + 6x IGCSE Extended = 15 questions), or a
           one-line preset ("15 questions, IBDP format")
        -> Generate (async job; Gemini API) -> Teacher reviews Answer Sheet + Question Sheet
        -> Confirm & Publish -> paper appears on the student's dashboard
        -> Student attempts it (MCQ/fill-blank auto-captured, subjective typed in)
        -> Submit -> auto-grade objective parts, LLM-grade subjective parts
        -> Teacher Dashboard shows marks + full answers, can override any grade
```

See the original architecture message in this feature's PR/session history for the full narrative (client UI mockup, ingestion layer, generation service, state machine, grading service, export layer) — this doc restates it as concrete, sequenced build phases rather than duplicating it wholesale.

## Why Gemini

Per explicit instruction, the LLM provider for generation and subjective grading is the **Gemini API** (not Claude/GPT) — this is a deliberate product choice, not a placeholder.

## Phase 1 — Data layer (done)

Applied via `supabase/migrations/20260715000000_homework_generator_phase1_schema.sql`. Seven new tables (36 total in `public` schema, up from 29):

- **`style_templates`** — reference library of exam-board/question-type prompt fragments (`code`, `board`, `question_type`, `prompt_fragment`). Empty until Phase 2 seeds it.
- **`content_uploads`** — teacher-uploaded PDF/PPT/DOCX source material, `parse_status` tracks whether the file has been consumed by generation (Phase 4: PDFs go straight to Gemini as a file part and flip to `completed`; PPT/PPTX/DOCX aren't supported yet and flip to `failed`).
- **`generated_papers`** — the core paper record: `student_id`, `created_by_teacher_id`, `content_source_type` (`session_log`/`upload`/`both`, CHECK-enforced against the matching FK actually being set), `blocks` (jsonb composition spec), `questions_json` (generated content, null until Phase 4), `status` driving the lifecycle (`draft` -> `published` -> `in_progress` -> `submitted` -> `graded`).
- **`question_bank`** — generated questions kept by `question_hash` for future dedup checks.
- **`submissions`** — one row per paper (`unique(paper_id)`), student's `answers_json`, immutable once `submitted_at` is set (enforced by the `prevent_submission_edit_after_submit` trigger, non-admin).
- **`grades`** — one row per submission, `per_question_json` (marks + AI feedback + teacher override per question), `total_marks`/`max_marks`.
- **`session_insights`** — optional structured extraction (topics/misconceptions/mastery) from a `session_logs` row, for Phase 4's prompt builder to consume later.

**Deliberately deferred to later phases** (kept out of Phase 1 to avoid untested schema-only automation):
- The `draft->in_progress`/`in_progress->submitted`/`submitted->graded` triggers described in the architecture's state-machine section are **not yet wired as DB triggers** — `generated_papers.status` will be advanced by application code (Phase 5's publish action, Phase 6's submit action, Phase 7's grading job) once those actually exist. Adding the triggers now, before anything writes to these tables, would be schema for its own sake.
- No vector/embedding storage — Phase 4 decided against it (see Phase 4's section below): source content is small enough, and PDF uploads go to Gemini as a file part, so no chunking/retrieval layer was needed.

**RLS pattern** (matches the rest of the schema — see `VERIFIED_DATABASE_STATE.md` §2.6): `is_admin()` gets `ALL` everywhere. A teacher gets `ALL` on rows they created (`created_by_teacher_id = my_teacher_id()` / `uploaded_by_teacher_id = my_teacher_id()`), mirroring how a teacher only ever sees their own `session_logs`. Performance coaches get blanket `ALL`/`SELECT` (matching the existing "Performance coaches can read all session_logs" blanket-access pattern rather than scoping through `pc_student_assignments`, since a PC routinely needs to see homework across all their students regardless of who generated it). Students get read-only access to their own non-draft papers/submissions/grades via the existing `can_view_student()` helper — they never see a `draft` paper.

Every new table has explicit `GRANT`s to `authenticated`/`service_role` (table privileges + identity-sequence `USAGE`) — this repo has hit "RLS policy correct but zero base grants" before (see `VERIFIED_DATABASE_STATE.md` §2.6), so grants are added alongside the tables rather than assumed.

## Phase 2 — Style Template Library (done)

Applied via `supabase/migrations/20260716000000_seed_style_templates.sql` (idempotent — `ON CONFLICT (code) DO UPDATE`, so wording tweaks can ship as their own re-runnable migration). 12 rows seeded, one per exam-format the teacher can pick in the composition builder, covering every active curriculum (`curricula` table — IBDP, IBMYP, IGCSE, AS & A Levels, AP, Standard Tests) plus the generic question types:

| `code` | `board` | `question_type` |
|---|---|---|
| `IBDP_SECTION_A` | IBDP | `structured` |
| `IBDP_SECTION_B` | IBDP | `extended_response` |
| `IB_MYP` | IBMYP | `criterion` |
| `IGCSE_CORE` | IGCSE | `structured` |
| `IGCSE_EXTENDED` | IGCSE | `structured` |
| `AS_A_LEVEL` | AS & A Levels | `structured` |
| `AP_MCQ` | AP | `mcq` |
| `AP_FRQ` | AP | `extended_response` |
| `MCQ` | — | `mcq` |
| `FILL_IN_BLANK` | — | `fill_blank` |
| `SHORT_ANSWER` | — | `short_answer` |
| `SUBJECTIVE` | — | `essay` |

Two deviations from Phase 1's tentative list, both deliberate: **AP was split into `AP_MCQ` + `AP_FRQ`** (AP genuinely assesses both, with different conventions), and a generic **`SHORT_ANSWER`** was added between fill-blank and full essay. No `STANDARD_TESTS` template — SAT/ACT/TOEFL/IELTS prep is best served by the generic `MCQ`/`SHORT_ANSWER`/`FILL_IN_BLANK` templates rather than a board-specific one; revisit if a distinct standardized-test format is wanted.

`question_type` is a **controlled value the generation (Phase 4) and grading (Phase 7) phases branch on**: `mcq` and `fill_blank` are auto-gradable by exact/fuzzy match; `short_answer` / `structured` / `extended_response` / `essay` / `criterion` are LLM-graded against the mark scheme. Each `prompt_fragment` is the actual instruction text handed to the Gemini prompt builder (format, command words, mark-scheme shape, expected length) — the `SUBJECTIVE`/essay one explicitly instructs the model to emit the mark scheme as a list of individually gradeable points, since Phase 7's grader depends on that.

## Phase 3 — Teacher UI skeleton (done)

Built at route **`/teacher/homework`** (`src/pages/teacher/TeacherHomeworkPage.tsx`), added to `App.tsx` for the `teacher` + `performance_coach` roles and to the teacher sidebar (`TeacherLayout.tsx`, new `IconPencil`). The page walks the four builder steps:

1. **Student** — `StudentSearch` picker.
2. **Content source** — Session log / Upload file / Both. The session-log dropdown is `useSessionLogs({ studentId }, teacher.id)` (the picked student's sessions, scoped to the caller's own logs). Uploads go to the private **`homework-content`** bucket and record a `content_uploads` row (`parse_status = 'pending'` — Phase 4 parses it).
3. **Composition** — Simple mode (one count + one style) or Blocks mode (repeatable count+style rows), plus a difficulty select; the total question count auto-sums.
4. **Generate draft** — validates, uploads any file, then writes a `draft` `generated_papers` row. `subject_id`/`curriculum_id` are inherited from the chosen session log. A right-hand "Your papers" list shows the teacher's papers with status badges.

Supporting code: `useStyleTemplates` (style dropdown), `useGeneratedPapers` (`uploadContent` + `createDraftPaper` + list). Phase 3 originally shipped a client-side stub (`src/utils/homeworkStub.ts`, `buildStubQuestions()`) that produced placeholder `questions_json` so the downstream UI had real data before Gemini existed; **Phase 4 removed that file** once real generation replaced it — the `GeneratedQuestion`/`GeneratedPaperContent` interfaces it defined now live in `src/types/database.ts` since they're the actual shape of `GeneratedPaper.questions_json`, not just a stub's shape.

New storage bucket migration: `supabase/migrations/20260717000000_homework_content_bucket.sql` (private `homework-content`, admin-manage / staff-read / staff-upload-under-`<student_id>/` policies, mirroring `report-cards`). TS types for all of this live in `src/types/database.ts` (`StyleTemplate`, `GeneratedPaper`, `ContentUpload`, `PaperBlock`, `QuestionType`, `PaperStatus`, etc.) and were checked against the live check constraints (`status` has no separate generating/failed value — a paper stays `draft` through generation; progress/failure is read from `questions_json`/`generation_error`).

## Phase 4 — Generation service (done)

Built as the **`generate-homework-paper`** Supabase Edge Function (`supabase/functions/generate-homework-paper/index.ts`), invoked by `useGeneratedPapers.createDraftPaper` right after the draft row is inserted (fire-and-forget from the client — the function writes its result straight to the row). `TeacherHomeworkPage.tsx`'s "Your papers" list polls every 4s (`useGeneratedPapers`'s interval effect) while any paper has `questions_json === null && !generation_error`, showing a "Generating…" badge; a "Generation failed" badge with the error text and a **Retry** button appears if `generation_error` gets set. `generated_papers.status` still doesn't move off `draft` here — per Phase 1's deferral, that's Phase 5's job.

**Auth model**: the function runs entirely as the calling teacher, not `service_role` — it builds its Supabase client from the caller's own JWT (anon key + `Authorization` header) so every read/write is enforced by the existing RLS policies (teacher-owns-the-paper / admin / performance-coach) rather than re-implementing that authorization check in function code. This only works because Phase 1 already gave staff `SELECT` on `style_templates` and `INSERT`/`SELECT` on `question_bank` — no new grants were needed for Phase 4.

**Pipeline**: load the draft paper + its blocks -> load the referenced `style_templates` rows -> resolve source content -> for each block, build one prompt (style's `prompt_fragment` + difficulty instructions + source content) and call Gemini (`gemini-2.5-flash` by default, `GEMINI_MODEL` secret to override) with `responseSchema`/`responseMimeType: application/json` structured output matched to that block's `question_type` -> validate count + required fields per question, retry once with the validation failure fed back into the prompt on mismatch -> merge all blocks -> for each question, hash `(style_code, question_type, normalized_prompt)` with SHA-256 and record it in `question_bank` (**as of 2026-07-14 the bank is written-only — no reuse-on-hit; see the "no-repeat generation" follow-up below** for why the old reuse behavior was removed) -> write the merged result to `questions_json` (shape: `GeneratedQuestion[]` + `total_questions`/`total_marks`, typed in `src/types/database.ts`) and clear `generation_error`. Blocks generate concurrently (`Promise.all`), not sequentially. Any failure at any step is caught and written to `generation_error` instead of left as a silent hang — the row is never left in an ambiguous "maybe still running" state beyond the poll interval.

**Two scope decisions made here** (resolving the two things Phase 1 explicitly deferred):
- **No vector/embedding store.** Session-log content is small enough (`fathom_summary` text) to paste directly into the prompt, and PDF uploads are handed to Gemini as a file part — neither needs retrieval-augmented chunking. Revisit only if source documents get large enough that a full document stops fitting in context.
- **Upload text extraction: PDF only, via Gemini's native file understanding — not a separate parse step.** The function downloads the PDF from the `homework-content` bucket and sends it to Gemini via the **Files API** — uploaded once (raw bytes streamed) and referenced by `fileData.fileUri` (`application/pdf`), *not* inlined as base64 (see the "Post-deploy fix" note below for why base64-inlining was removed). Gemini reads it directly, so `content_uploads.parsed_text` is intentionally left `null` for PDFs (`parse_status` still flips to `completed` once it's been used). **PPT/PPTX/DOCX uploads are not supported yet** — generation fails immediately with a clear `generation_error` ("...upload a PDF or use a session log...") rather than silently mis-parsing zipped XML. Building real PPT/DOCX extraction (or an OCR fallback) is follow-up work if a teacher actually needs it; nothing here blocks that being added later without a schema change (`content_uploads.file_type`/`parse_status` already accommodate it).

**Required secret**: `GEMINI_API_KEY` must be set on the edge function (`supabase secrets set GEMINI_API_KEY=...` or via the dashboard) — it is **not** set as part of this change, since it's a credential, not something a migration or MCP tool call can provision. Generation will fail with `"GEMINI_API_KEY secret is not configured"` until an admin sets it. Optional `GEMINI_MODEL` overrides the default model.

**Post-deploy fix — "both" content source silently ignored the session log (2026-07-09):** a real bug report — a paper generated with `content_source_type = 'both'` (a French-subject session log + an unrelated Science PDF) came back 100% Science content; the French session log was never drawn on at all despite being attached. Root cause in `generateOneBlock`'s prompt builder: the source-description line was a plain `sourceText ? "Base the questions on this source material: …" : "A source PDF is attached…"` ternary — for `'both'`, `sourceText` is always non-empty (the session-log branch runs unconditionally), so the prompt text described *only* the session log and never mentioned a PDF at all, even though `getPdfPart` still silently attached the PDF as a `fileData` part on every call regardless of `sourceText`. Gemini therefore received a text prompt pointing at the session log plus an unannounced, information-dense attached document — and leaned on the attached PDF instead. Fixed by passing a `hasPdf` flag into `generateOneBlock` and giving `'both'` its own explicit instruction naming *both* sources and telling Gemini not to ignore either one, instead of silently collapsing to a single-source description. Redeployed `generate-homework-paper` v18. (Investigated as part of the same report: an MCQ option that read "A. A vacuum" turned out to be correct behavior, not a bug — the genuine physics answer is "a vacuum," which just happens to start with the same letter as the UI's own "A." option label; verified live via `execute_sql` that only that one option coincidentally starts with its own letter and no systematic label-duplication exists in `questions_json`.)

**Post-deploy fix — question/mark-scheme mismatch (2026-07-08):** a published paper was found with a structured question (physics "work done" scenario) whose prompt was only a setup sentence — it never actually asked anything — while its `mark_scheme` graded a prediction ("the work done would double... because it's directly proportional to displacement") that no part of the prompt had asked for. `validateRawQuestion`'s shape checks (required fields present, correct types, right count) had no way to catch this, since a mark scheme grading an unasked question is still a structurally valid `{point, marks}` array. Two changes, both in `generateOneBlock`/`validateRawQuestion`:
- The per-block prompt (generic, applies to every style template) now explicitly instructs Gemini that every mark-scheme point must correspond to something the prompt itself explicitly asks, and to use labelled sub-parts `(a)/(b)/(c)` for multi-part questions.
- For every mark-scheme-graded type (`short_answer`/`structured`/`extended_response`/`essay`/`criterion`), `validateRawQuestion` now rejects a prompt that contains no question mark and none of a fixed list of command words (`Calculate`, `Explain`, `Define`, `Predict`, `what`/`why`/`how`, etc.) — a cheap, low-false-positive proxy for "this prompt actually asks something," since every legitimate exam question of this type is phrased as a question or instruction. A rejection routes through the existing validate/retry loop (`generateBlock`, 2 attempts, failure fed back into the retry prompt) rather than adding a new code path. This does not catch every possible content mismatch (it's a presence check, not true semantic verification against the mark scheme), but it directly closes the failure mode observed. Deployed as `generate-homework-paper` v11. The Phase 5 publish gate (human review before a paper reaches the student) remains the backstop for anything this heuristic misses.

**Post-deploy fix — English-only question heuristic failed every Language-Acquisition paper (2026-07-10):** a real bug report — generating an **IBDP French B** paper (paper 14, Simple mode, `IBDP_SECTION_A` + `IBDP_SECTION_B`, both mark-scheme-graded) failed outright with *"Block generation failed validation: prompt does not contain an explicit question/instruction …"*. Root cause: the `looksLikeAQuestion` command-word list added in the fix above was **English-only** (`Calculate`/`Explain`/`what`/`why`/…). A Language-B / ab-initio paper's prompts are written in the **target language** — French imperatives like *« Décrivez / Expliquez / Justifiez / Complétez / Relevez »* — so every generated question failed the check, both validate/retry attempts were exhausted, and `generation_error` was set. This affected *any* target-language subject (French/Spanish/German B, ab initio, IGCSE languages, etc.), not just this one paper. Two changes, both in `generate-homework-paper`:
- `QUESTION_COMMAND_WORDS` was extended with the common command verbs and interrogatives for **French, Spanish, and German** (infinitive + imperative forms), stored accent-stripped; `looksLikeAQuestion` now accent-normalizes the prompt (`NFD` → strip combining marks) before matching, so both accented (`Décrivez`) and unaccented model output is caught. The `?` short-circuit is unchanged. Matching leans deliberately lenient — a false "looks like a question" only skips a weak heuristic, whereas a false rejection breaks generation entirely (as it just did).
- The generic self-containment instruction in `generateOneBlock`'s prompt now notes that in a non-English target language the equivalent command word (or a `?`) is acceptable, so the model isn't nudged toward English phrasing.

Redeployed `generate-homework-paper` **v21**. The English scenario-with-no-question case the original fix targeted is still correctly rejected (verified against a set of French and English prompts); the Phase 5 publish gate remains the backstop.

## Phase 7 — Grading service (done)

New **`grade-homework-submission`** edge function (deployed, `verify_jwt = true`), invoked by the student on submit (and by the teacher "Grade now"/"Re-grade" buttons). Unlike the generation function it runs with **`service_role`**, because a student has no write access to `grades` or `generated_papers` — grading is a privileged action they only trigger. It still verifies the caller's JWT and authorizes it (admin / owning student / owning teacher / performance coach, mirroring the `grades` RLS) before doing anything.

Grading per question type: **MCQ** by exact option-index match, **fill-blank** by normalized string match against `expected_answer` + `acceptable_answers` (trim/lowercase/collapse-space/strip trailing punctuation) — both `graded_by: "auto"`. The **mark-scheme types** (`short_answer`/`structured`/`extended_response`/`essay`/`criterion`) go to **Gemini** with each mark-scheme point and its max, and it returns an awarded mark per point (clamped) + overall feedback — `graded_by: "ai"`. Results aggregate into `grades.per_question_json` (per-question `awarded`/`max`/`feedback`/`per_point`), `total_marks`, `max_marks`, and the function flips `generated_papers.status = 'graded'`.

**All subjective questions are graded in a single Gemini call** (`gradeSubjectiveBatch`, keyed by question id), not one call per question. This was a fix (2026-07-08): grading a paper with several mark-scheme questions used to fire one `generateContent` per question in sequence, which blew past the **Gemini free-tier limit of ~20 requests/minute** — the first couple of questions graded, then the tail came back 429 → "Automatic grading failed". One batched call keeps grading at a single request. Both `callGemini`s (grading and generation) now also **retry 429/503/500 with a backoff that honors the server's `retryDelay` hint** (up to 3 attempts, capped ~35s), and grading disables thinking (`thinkingConfig.thinkingBudget: 0`) since it's mechanical. The underlying free-tier RPM cap still exists — the durable fix for heavy use is enabling billing on the Gemini API (paid tier lifts 20 RPM to thousands); the batching + retry make normal single-paper generate-then-grade work within the free tier. Grade function redeployed v3, generate v10.

**Resilience**: if `GEMINI_API_KEY` is unset, or the batched grading call fails (e.g. rate limit even after retries), or the model omits a question, that subjective question comes back `awarded: 0` + "pending teacher review" instead of failing the whole submit — objective marks are still written, the paper still becomes `graded`, and the response carries `ai_incomplete: true`. The real cause is `console.error`'d for debugging. The teacher finalizes from there.

**Teacher override** lives on the existing review page (`/teacher/homework/:paperId`): once a paper is `submitted`/`graded`, that page swaps its draft editor for **`TeacherPaperResults`** (`useSubmissionGrade` hook) showing each question, the student's answer, the auto/AI mark + feedback, and a per-question override control. An override is a plain client `UPDATE` on `grades` (RLS: paper-owning teacher → `ALL`) that recomputes the effective total and stamps `teacher_reviewed_by`/`teacher_reviewed_at`; `gradeEffectiveMark()` makes an override supersede the AI mark everywhere it's displayed. A "Re-grade with AI" button re-runs the function (overwriting marks and clearing overrides). **AI marks are never presented as final without this path** — the student's score banner reads "not yet teacher-reviewed" until an override or review stamp exists.

**No schema change** was needed for Phases 6-7 — `submissions` and `grades` (Phase 1) already had every column (`answers_json`, `per_question_json`, `total_marks`, `max_marks`, `graded_at`, `teacher_reviewed_by`/`_at`). `GEMINI_API_KEY` is now set on the project, so subjective grading calls Gemini for real (see the batching/rate-limit note above).

## Follow-up (2026-07-08) — PDF chapter/section indexing + filterable session-log picker

Two additions after Phase 8, in response to teacher feedback. Neither is a new phase; both extend existing phases.

### PDF chapter/section indexing (upload → pick a chapter/section → generate from just that part)

Previously an uploaded book/notes PDF was always used whole. Now a teacher can generate homework from any combination of chapters/sections of it.

- **Schema** (`supabase/migrations/20260718000000_homework_pdf_outline_scope.sql`): `content_uploads` gained `outline` (jsonb — the chapter→section tree with page ranges), `outline_status` (`pending`/`processing`/`completed`/`failed`, its own async-job lifecycle, *separate* from `parse_status`) and `outline_error`. `generated_papers` gained `content_scope` (jsonb, null = whole document; otherwise `{ label, page_start, page_end, parts? }` — `parts` is an array of the selected `{ label, page_start, page_end }` slices, `label`/`page_start`/`page_end` being a summary + bounding span; a legacy value with no `parts` is treated as one implicit part). Types: `ContentOutline`/`OutlineChapter`/`OutlineSection`/`ContentScope`/`ContentScopePart` in `src/types/database.ts`. No migration was needed to add multi-part selection — `content_scope` is jsonb and the shape was extended additively.
- **`index-content-upload` edge function** (new, `verify_jwt = true`, runs as the calling teacher like generation): downloads the PDF, calls Gemini with a structured-output schema to extract the chapter→section outline (page ranges within the physical PDF), and writes it to `content_uploads.outline`. PDF-only — non-PDF uploads flip straight to `outline_status = 'failed'`.
- **Upload flow change** (`useContentUpload` hook + `TeacherHomeworkPage`): the file now uploads **as soon as it's picked** (not at Generate time), so indexing can run and the teacher can choose the scope before generating. The page polls `outline_status`, then renders `ContentScopePicker` — a **checklist** of every chapter and section (a "Whole document" checkbox at the top; each chapter row is a "whole chapter" checkbox with its sections as indented checkboxes) where the teacher can tick **any combination** of parts. The resulting `ContentScope` (summary label + bounding span + the ticked `parts`, or null for whole document) is stored on the draft via `createDraftPaper`. Indexing failure is non-fatal — the teacher can retry or just generate from the whole document.
  - **Fixed 2026-08-04 — ticking one row ticked its same-page siblings.** A `ContentScopePart` has no id, and the picker decided which rows to render checked by comparing **page ranges only**. Any rows sharing a range were therefore indistinguishable: a one-page chapter whose four sections all sit on that page (an "Implementation" chapter on p.3 with four p.3–3 sections) rendered all five boxes ticked from a single click. Only the display was wrong — the emitted scope, and the summary line under the list, always held the one part actually selected — but there was no way to tell what would be generated. Identity is now **label + page range**; the rules moved into `src/utils/contentScope.ts` (`samePart` / `isPartSelected` / `togglePart` / `selectedPartsOf` / `buildContentScope`) and are unit-tested in `contentScope.test.ts`, including this exact same-page-siblings outline. The label is what distinguishes such slices downstream too, since the scoping prompt names it alongside the page range (next bullet).
- **Generation change** (`generate-homework-paper`, redeployed version 9): when `content_scope` is set (and there's a PDF), the per-block prompt gets a scoping instruction — for a single part, "IMPORTANT: draw only from pages X–Y (`label`)"; for multiple parts, a bulleted list of every selected part's label + page range with "spread the questions across them, ignore every other page/section". Gemini still receives the whole PDF as a file part — the scoping is by instruction, not by physically slicing pages (no PDF-splitting library in the Deno runtime). Deliberate: good enough for the small documents in scope; revisit with real page extraction if teachers report leakage across sections.

**Reuse of uploaded materials:** every upload is a persisted `content_uploads` row (in the private `homework-content` bucket) with its `outline` stored once extracted, so it stays available later. The Homework Generator shows a **"Reuse a previously uploaded file"** dropdown — picking one adopts it (and its existing index) without re-uploading or re-indexing. A newly uploaded file is added to that list too. **As of 2026-07-14 this spans every student the teacher has uploaded for, not just the one currently picked** (`useTeacherUploads(teacherId)`, renamed from the original `useStudentUploads(studentId, teacherId)` — the DB/storage RLS was already scoped by `uploaded_by_teacher_id`/staff-read only, never by student, so this was a frontend query fix, not an access-control change). A teacher commonly reuses the same source PDF (e.g. a textbook chapter) across several students, and the old per-student scoping hid it the moment they switched students. The picker now shows each option's `student_id` (matching how the existing "reuse an existing paper" picker already displays it) so the teacher can tell entries apart; adopting one for a different student leaves the `content_uploads` row's own `student_id` as-is (it just records who first uploaded it) and the new paper's `content_upload_id` simply points at the same row — the same pattern "reuse an existing paper" (`cloned_from_paper_id`, above) already established for not duplicating content across students.

**Post-deploy fix (memory) — round 1 (superseded by round 2):** the first live run of `index-content-upload` returned Supabase status **546** (worker killed) on a real textbook PDF. First-diagnosed cause: base64-encoding the PDF by building a string one char at a time (`binary += String.fromCharCode(...)`) is O(n²) memory. Switched both functions to `encodeBase64` (std, single pass) with a ~14MB cap. This reduced but **did not eliminate** the 546.

**Post-deploy fix (memory) — round 2 (2026-07-08, current):** `index-content-upload` still returned **546 at ~3.5s** on a 7.35MB PDF (`iesc107.pdf`) — well before a Gemini call could return, and both `content_uploads` rows were still `parse_status: pending`, i.e. the PDF had never actually been processed by *either* function (`generate-homework-paper`'s earlier 200 ran off a session log, not this upload). Root cause: even with single-pass `encodeBase64`, **inlining a multi-MB PDF as base64 into the Gemini JSON request** holds the raw bytes + a UTF-16 base64 string (2 bytes/char) + the `JSON.stringify`'d body + the UTF-8 fetch encoding all in memory at once, which blows the worker's limit. Fix: **stop inlining base64 entirely and use the Gemini Files API** — a new `uploadPdfToGemini` helper (in both functions) uploads the raw PDF bytes once via the resumable upload protocol (`X-Goog-Upload-Command: start` → returned upload URL → `upload, finalize`, streaming the `Uint8Array` as the request body, no base64, no giant JSON), waits for the file to become `ACTIVE`, and the `generateContent` call now references it by `fileData.fileUri` instead of `inlineData.data`. Worker memory stays flat at ~the file size, so the cap was raised to ~50MB (the Files API itself allows up to 2GB / 48h retention). The client-side killed-worker guard from round 1 (a `processing` outline unresolved within ~2 minutes, or an errored invoke, is marked `failed` with a Retry) is unchanged. Functions redeployed (`index-content-upload` v3, `generate-homework-paper` v8). Not yet exercised against live Gemini from the sandbox (no browser egress — same caveat as every phase); the fix was confirmed against the live 546 logs and the documented Files API protocol, and needs one real "Retry indexing" / "Generate draft" click-through to close out.

**Not exercised end-to-end against live Gemini from this sandbox** (same caveat as every phase) — verified via clean `tsc -b`/`vite build`, applying the migration, and deploying both functions through the Supabase MCP connection. Whoever runs the first real click-through should sanity-check the extracted page ranges against a couple of known PDFs and tune the index prompt if Gemini's physical-vs-printed page numbering drifts.

**Post-deploy fix — client was erasing the real indexing error (2026-07-08):** a fresh 500 on `index-content-upload` (`iesc109.pdf`, ~5-7s execution — not the round-2 546/memory failure, which is confirmed fixed by successful indexes in between) turned out to be undiagnosable from the DB: `content_uploads.outline_error` only ever showed the generic client-side fallback ("Indexing failed to complete. Retry, or generate from the whole document."), never the specific reason. Root cause was in `useContentUpload.ts`'s `triggerIndex`: the edge function's own `catch` block already writes a specific `outline_error` before returning its non-2xx response, but the client's `.then(({error}) => markFailed(...))` unconditionally overwrote it with the generic message on every invoke error, destroying the real cause every single time. Fixed by refetching the row first and keeping the specific error if the edge function had already written one, falling back to the generic message only when it genuinely hadn't (e.g. the worker was killed outright before its catch could run).

**Post-deploy fix — index-content-upload had no 429 retry (2026-07-08, same day, found once the above fix surfaced the real error):** with the error message no longer being erased, the real cause showed up immediately — `Gemini API error (429)`, `RESOURCE_EXHAUSTED`, free-tier `generate_content` quota (20 requests/minute) exceeded. Phase 7 added 429/503/500 retry-with-backoff (honoring Gemini's `retryDelay` hint, up to 3 attempts) to both `generate-homework-paper` and `grade-homework-submission`'s `callGemini` — **`index-content-upload`'s `callGemini` was missed** and had no retry at all, so it failed hard on the first rate-limit hit instead of waiting it out like the other two functions. Added the same retry loop (`parseRetryDelayMs`, `MAX_GEMINI_ATTEMPTS = 3`) to `index-content-upload`, deployed v4.

**Post-deploy fix — retry wait cap was shorter than Gemini's own hints (2026-07-08, same day):** heavy back-to-back testing (multiple PDF indexes + paper generations in a short window) kept re-exhausting the free-tier quota, and Gemini's `retryDelay` hints observed in practice (36.9s, then 59.8s on a second hit) were longer than all three functions' `MAX_RETRY_WAIT_MS` cap of 35000ms — so a retry would wait the capped 35s, still land inside the quota window, and burn through all 3 attempts without success even though the *next* attempt would likely have worked. Raised `MAX_RETRY_WAIT_MS` to 60000 in all three (`generate-homework-paper` v12, `index-content-upload` v5, `grade-homework-submission` v4) so a single Gemini-directed wait is actually honored instead of cut short. Also raised `useContentUpload.ts`'s client-side "dead worker" grace window from 120s to 240s — with retries now able to wait up to 60s twice, a legitimate in-progress retry could exceed the old 2-minute window and get wrongly marked failed by the client while the function was still working. The underlying free-tier RPM cap is unchanged — the durable fix for heavy use is enabling billing on the Gemini API project (see Phase 7's note); this just makes the free tier's own retry hints actually work instead of being cut off.

**Feature — multi-key rotation across the Gemini free tier (2026-07-09):** the raised retry cap above still only stretches a single project's 20 RPM quota so far. To actually raise the effective ceiling, all three Gemini-calling functions (`generate-homework-paper`, `index-content-upload`, `grade-homework-submission`) now support rotating across multiple API keys, each read via a shared `getGeminiKeys()` helper: the required `GEMINI_API_KEY` plus optional `GEMINI_API_KEY_2` through `GEMINI_API_KEY_8`. Each key is expected to belong to a **separate Google Cloud project** so it carries its own independent free-tier quota — two keys from the same project share one quota pool and rotating between them does nothing.

`callGemini` in all three functions now sweeps the whole key ring on a transient failure (429/503/500) — trying every configured key once, immediately, before falling back to waiting out the last key's retry-hint and sweeping again (`MAX_GEMINI_ATTEMPTS` is now "number of sweeps," not "retries on one key"). A non-transient failure on every key (e.g. every key is malformed) aborts immediately rather than uselessly sweeping again.

**The one real complication:** Gemini's File API scopes an uploaded file to the project that uploaded it — a `fileUri` from key A's project is not valid for a `generateContent` call made with key B. `generate-homework-paper` and `index-content-upload` both upload a PDF once and reference it by `fileUri`, so naive key-swapping-on-retry would fail with "file not found" the moment two different keys got used across a retry. Fixed by deferring the actual Gemini upload out of `resolveSource`/the download step entirely — those now only return raw bytes — and introducing a **per-key, memoized upload provider** (`makePdfPartProvider` in `generate-homework-paper`, inlined per-sweep-per-key in `index-content-upload`): the first attempt with a given key uploads the PDF under that key's project and caches the in-flight promise (so concurrent blocks in `generate-homework-paper`'s `Promise.all` that happen to try the same key share one upload instead of each re-uploading); a later attempt that rotates to a different key re-uploads fresh. `grade-homework-submission` has no file dependency (text-only prompts), so its rotation is a simple per-attempt key swap.

No schema change, no new edge function — this is a code-only change to the three existing functions. Deployed `generate-homework-paper` v17, `index-content-upload` v10, `grade-homework-submission` v9. **The 4 additional keys are not yet set as secrets** — Supabase secrets can only be set via the dashboard (Project Settings → Edge Functions → Secrets) or `supabase secrets set`, neither of which this session had access to (no Supabase CLI, no MCP tool for secrets). Whoever has dashboard access needs to add `GEMINI_API_KEY_2` through `GEMINI_API_KEY_5` before rotation actually does anything — until then `getGeminiKeys()` just returns the single existing `GEMINI_API_KEY` and behavior is unchanged from the retry-cap fix above.

### Subject-hierarchy templates (2026-07-21) — resolve the exact template per subject/level

Until now the style-template library was flat: one `style_templates` row per exam-format, keyed only by `code` + `board`. A single `IBDP_SECTION_A` was used identically for IBDP Maths, English and Physics — but "Section A" genuinely differs by subject (an IBDP English SL guided textual analysis vs an IBDP Maths SL structured calculation) and by level (SL vs HL depth). This change lets a template hang off the **real, existing subject hierarchy** (curriculum → group → subject, with level carried inside the subject row since SL/HL are separate `subjects` rows) and makes generation resolve the exact one.

- **Schema** (`supabase/migrations/20260721000000_style_templates_subject_hierarchy.sql`): `style_templates` gained `section_key` (not null — groups a family of variants), real FK columns `curriculum_id` / `curriculum_group_id` / `subject_id` (all nullable; null = "applies at any value here"), and `is_selectable` (default true). No re-typed subject names — the hierarchy is referenced by FK so it can't drift from the live `curricula`/`curriculum_groups`/`subjects` data. Backfill set `section_key = code` and `curriculum_id` from `board` for the original 12 rows, so each became the curriculum-level fallback of its own family. Four partial unique indexes enforce one row per specificity slot per family (deterministic resolution); a `section_key` index speeds lookup. See `VERIFIED_DATABASE_STATE.md` §`style_templates` for the column table.

- **Resolver** (`generate-homework-paper`, redeployed **v19**): a new `resolveTemplate(client, familyCode, hier)` replaces the old `loadTemplates` code-lookup. For each block, it loads the picked template (the family head, still identified by `block.style`), reads every active variant sharing its `section_key`, and picks the **most specific one that matches the paper's place in the hierarchy** — scoring `subject_id` match (3) > `curriculum_group_id` (2) > `curriculum_id` (1) > generic (0), disqualifying any variant whose pinned field doesn't match. `loadPaperHierarchy` fetches the paper's subject's `curriculum_group_id` (one hop up; `subject_id` already carries the level). If nothing qualifies (e.g. a paper whose curriculum doesn't match the picked head), it returns the picked head — **never worse than before this feature**. The resolved variant's `prompt_fragment`/`question_type`/`code` drive generation and `question_bank` dedup, but the stored `GeneratedQuestion.style` stays the **family code** the teacher picked, so the review page's per-block header (`styleName(block.style)`) still resolves against the selectable library.

- **Selection UX — a Type → Subject → Section funnel, not two parallel pickers (2026-07-21, v20; reworked same day).** The first cut added a subject picker (Curriculum → Group → Subject → SL/HL) *alongside* the existing flat "Style" dropdown — two independent controls, confusing (the style dropdown already named a curriculum, e.g. "IBDP — Section A", then a second, separate Curriculum dropdown asked again) and it defaulted to the first template on load, hiding that a choice was even being made. Replaced with a single funnel per block (and once for the whole paper in Simple mode):
  1. **"Question type" select** — the 12 selectable templates split into **generic** (`board IS NULL`: MCQ / Fill-in-blank / Short answer / Subjective — picking one is the *complete* choice, no subject asked) and **curriculum** (one entry per distinct `board`: IBDP / IBMYP / IGCSE / AS & A Levels / AP — picking one names *only* the curriculum, not a section yet, encoded as a `curriculum:<board>` option value so it doesn't collide with a real template code). Standard Tests has no dedicated template family (deliberate Phase 2 decision) and so isn't offered here — only the boards that actually have templates appear.
  2. **If a curriculum was picked** — `AcademicSubjectPicker` renders **without its own Curriculum dropdown** (new `lockCurriculum` prop: the curriculum is already decided by step 1, so only Group → Subject → SL/HL is asked) for that fixed curriculum.
  3. **Section, only in Blocks mode** — if the curriculum has more than one template (IBDP: Section A/B; IGCSE: Core/Extended; AP: MCQ/FRQ; IBMYP and AS & A Levels have exactly one, so no Section control is shown at all), a "Section" dropdown lets the teacher pick which one this block is. **Simple mode never shows this** — picking a curriculum in Simple mode fans the single Type choice into one hidden block per section behind the scenes (`splitCount`, remainder-first), so e.g. 15 questions of "IBDP" mixes ~8 Section A + ~7 Section B automatically, matching how a teacher actually thinks about "give me an IBDP paper" vs. a Blocks-mode teacher deliberately composing 4 Section A + 5 Section B.
  - **Per-block subject on the model + resolver.** `PaperBlock` gained optional `subject_id`/`curriculum_id` (persisted in the `blocks` jsonb — no schema change). The edge function resolves **per block**: `hierarchyForBlock` uses the block's own subject when set, else the paper-level subject (`hierarchyForSubject`, which replaced `loadPaperHierarchy`). The paper-level `subject_id`/`curriculum_id` are set from the first effective block for display/back-compat.
  - Session-log selection still prefills Simple mode's Type + subject when the log's curriculum has a known template family, so the common case (generate from a session log) needs no extra clicks; still fully overrideable.

- **Seeded templates.** Three layers, all under the same `section_key` families, so the resolver picks the most specific one present:
  - **Generic family heads (12, `is_selectable=true`)** — the only rows in the teacher's picker (Phase 2 library); every paper falls back to these.
  - **Group-level (50, `is_selectable=false`, `20260722000000_style_templates_group_level_all_curricula.sql`)** — one per (curriculum group × the section-families that curriculum uses): IBDP 7 groups × Section A/B, IBMYP 9 × criterion, IGCSE 5 × Core/Extended, AS & A Levels 5 × structured, AP 6 × MCQ/FRQ. Each carries an area-specific `prompt_fragment` (Sciences = data-response/method marks, Individuals & Societies = source analysis + essay, Language Acquisition = target-language text-handling, etc.). This is what makes **all 453 subjects** resolve to a subject-area-appropriate template via the `curriculum_group_id` layer — e.g. IBDP French B → `IBDP_SECTION_A__LANGACQ`. AP Capstone was intentionally excluded (performance-task assessed, not MCQ/FRQ — it falls back to the generic AP head). Groups are matched by (curriculum, group name), not hardcoded ids.
  - **Subject-level overrides (4, `is_selectable=false`)** — IBDP English A: Lang & Lit SL/HL and IBDP Maths A&A SL/HL under `IBDP_SECTION_A`, which win over the group-level template for those exact subjects/levels.
  Add more specific rows over time via the same migration pattern (a subject/group/curriculum FK + a shared `section_key`); no code change is needed for a new variant to start resolving. There is no admin UI for the template library yet — it's managed via migrations (deliberate scope).

## Parse an existing paper (2026-07-26)

A second way to get a paper onto a student's dashboard, alongside "generate from a session log / upload" and "reuse another student's paper": **upload an existing paper and have Gemini read the questions straight off it.** The teacher isn't composing anything and no new questions are invented — the questions are the uploaded paper's own. Everything after extraction (review, edit, publish, student attempt, auto/AI grade, teacher override, export) is the *same* flow every other paper goes through, because a parsed paper writes the identical `questions_json` shape.

**Why this exists:** teachers often already have the paper they want to set (a past exam, a worksheet, a textbook exercise) as a PDF or just on paper. Regenerating an approximation of it via the composition builder is wasted effort and produces different questions. This lets them use the real thing, and still get the platform's answer key + AI grading on top.

### The flow

```
Teacher opens Homework Generator -> picks the student -> "Or upload an existing paper" card
        -> uploads a PDF, or takes/chooses a photo of the paper (camera capture on mobile)
        -> a `parsed` draft paper is created and parse-homework-paper is fired
        -> teacher lands on the review page, watches it parse ("Reading the uploaded paper…")
        -> reviews the extracted Question Sheet / Answer Sheet, edits anything the parse got wrong
        -> Confirm & Publish  ->  (from here identical to every other paper)
        -> student attempts it -> submit -> MCQ/fill auto-graded, subjective AI-graded -> teacher publishes the grade
```

There is **no composition step, no style-template selection, no difficulty, and no session log** — the paper's structure comes entirely from the uploaded document.

### Data model

- **`content_source_type = 'parsed'`** (5th value, `20260726000000_homework_parse_existing_paper.sql`). `generated_papers_source_check` was rewritten so `parsed` requires `content_upload_id` (same rule as `upload`); no session log, no `content_scope`. **Multi-page (`20260727000000_homework_parse_multi_page.sql`):** a paper photographed across several pages stores every page's upload id in the ordered array **`content_upload_ids`** (`bigint[]`, nullable), with `content_upload_id` kept set to the first element so the source-check and every single-file paper are untouched (null array = single-file, use `content_upload_id`). An array column, not a join table, for consistency with the other array/jsonb columns here. `blocks` starts `[]` at insert and is overwritten by the edge function with **one display-only block per extracted section** — the section title goes in `block.style` (which is a `style_templates.code` for generated papers but here is just a label; `styleName()` on the review page returns an unknown code unchanged, so the section title renders as the block header). Each `GeneratedQuestion.style` is set to the same section title.
- **`content_uploads.file_type`** now also accepts image types (`jpg`/`jpeg`/`png`/`webp`/`heic`), so a photo/scan is a valid upload — not just documents. A parsed upload is **never indexed** into chapters (`outline_status = 'failed'`); its lifecycle is `parse_status`, driven by `parse-homework-paper`.
- No new table, no RLS change. The teacher-owns-own-row policies on `generated_papers`/`content_uploads` and the path-scoped `homework-content` staff-upload storage policy already cover it (the storage policy gates on the `<student_id>/` path prefix, so image extensions upload fine).

### `parse-homework-paper` edge function

New function (`verify_jwt = true`), runs as the **calling teacher** (anon key + caller JWT, RLS-enforced — no `service_role`), mirroring `generate-homework-paper`. Body `{ paper_id }` parses (or re-parses) the paper's uploaded file.

- **File(s) → Gemini via the File API** (`uploadFileToGemini`, generalized from generation's `uploadPdfToGemini` with a MIME-type parameter): PDF and images alike are streamed once as raw bytes and referenced by `fileUri` — never base64-inlined (the 546-OOM lesson from generation applies equally here). A **multi-page paper sends one file part per page**, in order — `makeFilePartsProvider` uploads every page under the active key (per-key memoized, in parallel; a `fileUri` is scoped to the key's project so the multi-key rotation re-uploads on a key switch) and the prompt gets a note that the files are consecutive pages of one paper. The combined resident size is capped at ~50MB (`MAX_TOTAL_BYTES`) and the page count at 20 (`MAX_PARSE_FILES`) so a pile of photos can't OOM the worker.
- **Mixed-type structured output.** Unlike generation (one block = one `question_type`, so a rigid per-type schema works), a real paper mixes types in one document. The response schema is `{ sections: [{ title, questions: [q] }] }` where each `q` has `question_type` (enum) + `prompt` + `marks` **required** and every type-specific field (`options`/`correct_option`/`expected_answer`/`acceptable_answers`/`mark_scheme`) **optional**. Code normalizes/coerces afterward (`normalizeQuestion`).
- **The prompt** instructs Gemini to transcribe every question verbatim (no inventing/merging/dropping/rewording, fix only OCR noise), classify each type, and read the marks off the paper. For the **answer key it decides per question**: it first checks whether the paper already marks the answer (a tick/cross against options, a highlighted/circled/bold/coloured correct option, an 'Ans:'/'Answer:' label, a worked solution, or a separate answer-key/solutions section) and, when it does, **uses the paper's own answer as authoritative** (never overriding it); only when a question has no marked answer does it **build the answer key itself** (MCQ correct option, fill-blank expected answer + variants, or a mark scheme of creditworthy points). This matters because uploaded papers frequently already carry a marked answer key — the earlier prompt assumed "questions only" and always re-derived answers, which could silently override the paper's own. Low temperature (0.2) — this is transcription, not creation.
- **Lenient normalization.** A real paper's text is authoritative, so nothing is rejected the way generation's `validateRawQuestion` rejects a scenario-with-no-question. Anything unreadable as its declared type (an "MCQ" with no options, a "fill_blank" with no answer, or any mark-scheme type with an empty scheme) is **downgraded to a mark-scheme question** with a synthesized single point, so it's still gradable and the teacher can fix it in review — never dropped. Empty-prompt questions are skipped. If the whole extraction yields zero questions, it retries once, then fails with a clear "couldn't find any questions" error written to `generation_error` (same failure surface as generation).
- Reuses generation's multi-key rotation / 429-503-500 sweep + retry-hint backoff (`getGeminiKeys`, `callGemini`, `MAX_GEMINI_ATTEMPTS`, `MAX_RETRY_WAIT_MS`).
- **Latency + answer-reading accuracy (2026-07-14).** The extraction call uses a **bounded `thinkingConfig: { thinkingBudget: 4096 }`** — deliberately neither the default *unbounded/dynamic* thinking nor fully disabled. Gemini 2.5 Flash's default dynamic thinking over a whole 100-question multimodal paper was overrunning the edge worker's ~150s wall-clock limit and returning a **504 with no `generation_error` written** (the catch never runs on a platform kill), leaving the paper stuck on "Parsing…" forever. Fully disabling thinking (`thinkingBudget: 0`) fixed the timeout but made the model **misalign a marked answer key** — it read a paper's ✓/✗ option marks against the wrong option on some questions (e.g. defaulting to the first option). The bounded budget keeps the timeout headroom (a thinking-off parse of a 100-question paper ran ~60s) while restoring enough reasoning to read the marks correctly. Belt-and-braces: each `generateContent` fetch is bounded by an **`AbortController` timeout** (`GEMINI_CALL_TIMEOUT_MS`, 110s) that fails fast into a clean surfaced error instead of a silent 504, and the paper's page(s) are **downloaded from storage in parallel** (`Promise.all`) rather than one blocking `await` per page.

### Frontend

- **`useGeneratedPapers.parseExistingPaper(studentId, teacherId, files)`** — takes an array (a single PDF, or several images — a mix of multiple PDFs is rejected, count capped at `MAX_PARSE_FILES`), validates each extension (PDF + image types), uploads each to `homework-content`, inserts a `content_uploads` row per page (not indexed), then a `parsed` draft `generated_papers` row (`content_upload_id` = first id, `content_upload_ids` = the full ordered list when there's more than one), fires `parse-homework-paper`, and returns the draft. `retryGeneration` now dispatches to `parse-homework-paper` vs `generate-homework-paper` by the paper's `content_source_type`.
- **`useGeneratedPaper.regenerate`** (review page) routes to `parse-homework-paper` for a parsed paper (ignoring any block/question scope — there's no per-question AI regeneration for a parsed paper), else to `generate-homework-paper` as before.
- **`TeacherHomeworkPage`** — a new **"Or upload an existing paper"** card (shown once a student is picked) with a `multiple` PDF/image file input (`accept` includes `image/*,application/pdf`, so mobile offers camera + photo library + files; selecting several photos parses them as one multi-page paper). On file select it uploads, creates the parsed draft, and navigates straight to the review page. The "Your papers" list shows **"Parsing…" / "Parse failed"** (instead of Generating/Generation failed) for parsed papers.
- **`TeacherHomeworkReviewPage`** — for a parsed paper: the header reads "Parsed from an uploaded paper…"; the in-progress card reads "Reading the uploaded paper…"; the failure card reads "Parsing failed" / "Retry parsing"; the **per-question and per-block AI "Regenerate" controls are hidden** (there's nothing to regenerate — inline **Edit** is the review tool), and the footer's bulk action becomes **"Re-parse paper"** (re-runs extraction on the same upload). `QuestionReviewCard` gained a `canRegenerate` prop for this. Inline editing, Confirm & Publish, the three tabs, and export are all unchanged.

### Deliberate scope / follow-ups

- **A parsed paper is one PDF, or several photos** (one per page, up to `MAX_PARSE_FILES` = 20, combined ≤ ~50MB). A single PDF can be multi-page as before; a multi-page paper shot as several photos is now supported too (2026-07-27 — `content_upload_ids`). Mixing multiple PDFs into one paper is deliberately rejected (stitch them into one PDF instead). Very long papers beyond the count/size caps would need chunked extraction — a reasonable follow-up if it ever comes up.
- **Extraction quality is Gemini's OCR + judgement**, so review-before-publish is the backstop (as it is for generation). The teacher can fix any misread question or answer inline before publishing, and the answer key it builds should always be sanity-checked. **Not yet exercised end-to-end against live Gemini from the build sandbox** (same egress caveat as every phase) — whoever runs the first real click-through should try a PDF and a phone photo and tune `EXTRACTION_PROMPT` against real output.

## Parsed-paper format preservation — Markdown tables + cropped figures (2026-07-14)

Teacher feedback: parsing an existing paper transcribed only the text, so a past paper with a data table (e.g. a schedule of hours) or a diagram (a pie chart, a bar-chart grid to complete) came back with the table collapsed into run-together prose and the diagram silently dropped. Two additions to `parse-homework-paper`, both flowing through the *same* `questions_json` shape everywhere downstream (review, attempt, export) rather than adding a parsed-paper-only code path:

- **`prompt` is now Markdown, not plain text.** `EXTRACTION_PROMPT` instructs Gemini to transcribe a data table on the page as a real GitHub-Flavored-Markdown table (`| … | … |` + header separator), preserving every row/column (including a cell the student must fill in, left genuinely blank). `GeneratedQuestion.prompt` (`src/types/database.ts`) is documented as Markdown; generated (non-parsed) prompts are unaffected since plain prose is valid, unstyled Markdown.
- **`GeneratedQuestion` gained an optional `figures: QuestionFigure[]`** (`{ data_url, alt? }`) — a genuine visual (pie chart, graph, geometric diagram, a blank axes grid) that Markdown can't represent. Gemini locates each figure with a `page_index` + `box_2d` (0–1000 normalized bounding box, the standard Gemini vision convention) instead of trying to describe it in text; `parse-homework-paper` then **crops that exact region out of the uploaded page's own pixels** (new `cropFigureFromImage`/`resolveFigures`, using the `imagescript` Deno module already vendored for this kind of raster work) and stores it inline as a small downscaled (≤900px) `data:` URL — the real image from the paper, not a redrawing. Best-effort throughout: an undecodable page (HEIC — `imagescript` only reliably decodes jpg/png) or a degenerate box just means that question has no figure, never a hard parse failure. Capped at 4 figures/question.
- **Client-side PDF rasterization is now required for figure cropping.** Cropping needs real pixels; a raw PDF byte stream can't be decoded/cropped in the Deno edge runtime the way an image can. `src/utils/rasterizePdf.ts` (new, `pdfjs-dist`) renders a PDF's pages to PNGs in the browser *before* upload, so a PDF is uploaded as one page-image per page — indistinguishable, from the edge function's point of view, from a teacher having photographed each page (same `content_upload_ids` multi-page path). Capped at the same `MAX_PARSE_FILES` (20) as photo uploads; a longer PDF surfaces a clear error asking the teacher to split it, rather than silently truncating. If rasterization itself fails (a corrupt/encrypted PDF), `useGeneratedPapers.parseExistingPaper` falls back to uploading the raw PDF — transcription still works via Gemini's own PDF reading, it just can't crop figures off it.
- **Rendering.** New `src/components/homework/QuestionContent.tsx` (`react-markdown` + `remark-gfm` + `remark-breaks` — the last one keeps a bare single newline behaving like the old `whitespace-pre-wrap` did, since strict CommonMark would otherwise swallow it) is the one place a question's prompt+figures render — used by `QuestionReviewCard` (both Answer/Question sheet modes), `QuestionAttemptCard` (student view), and `TeacherPaperResults` (Student's Answers tab), replacing each one's own plain `<p>`. Figures render as click-to-enlarge images after the prompt text.
- **Export.** `src/utils/exportHomeworkPaper.ts` gained a small Markdown→blocks parser (`src/utils/markdownBlocks.ts`, paragraphs + GFM tables, inline emphasis stripped to plain text — full inline rich-text wasn't worth the extra plumbing since the table structure was the thing actually being lost) so a transcribed table renders as a real table in both outputs — `jspdf-autotable` for PDF, a `docx` `Table` for DOCX — and figures embed as images (`doc.addImage` / `ImageRun`), sized to fit without distorting aspect ratio (an `<img>` preload recovers each figure's natural pixel size first). Both export functions are now `async` for this (`exportHomeworkPaperPdf` wasn't before); the caller (`HomeworkExportButtons.tsx`) already just fires-and-forgets on click, so no change needed there.
- **New dependencies**: `pdfjs-dist`, `react-markdown`, `remark-gfm`, `remark-breaks` (frontend); `imagescript` (Deno, `parse-homework-paper` only — vendored via its `deno.land/x` URL import like the rest of this function's dependencies, no `deno.json` needed). No schema change — `figures` is an additive optional key inside the existing `questions_json` jsonb column.

**Post-deploy fix — figures rendered visibly cut off, and multi-page PDFs were slow to parse (2026-07-14, same day):** the first real live parse (a 16-page IGCSE past paper) surfaced two problems at once:
- **Corrupted figure crops.** Every cropped figure (a pie chart, in the reported case) rendered with its bottom portion missing/cut, not a clean failure. Root cause: `cropFigureFromImage`'s `encodeJPEG()` call (ImageScript) was silently returning **truncated JPEG bytes — confirmed by pulling a stored figure directly out of the DB and finding no end-of-image marker at all** — without throwing, so the function's own try/catch never caught it and the broken bytes were stored as-is. Most browsers decode a truncated baseline JPEG leniently instead of erroring (no `onerror`), which is exactly why it *rendered*, just partially, instead of showing the "figure could not be displayed" fallback `QuestionContent.tsx` already has for a genuinely broken image. Fixed by switching to ImageScript's **PNG** encoder (`.encode()`, compression level 6) — the more heavily-used/tested path in this library, and, being lossless, also a better fit for line-art diagrams/charts/text than JPEG's lossy DCT compression anyway — plus a new `isValidPng()` signature+trailer check so that if any future encode path ever produces bad bytes again, the figure is silently skipped rather than persisted corrupt. `QuestionFigure.data_url` is now `image/png`; `exportHomeworkPaper.ts`'s PDF (`doc.addImage`) and DOCX (`ImageRun`) figure embedding were both changed to read the actual mime subtype off the data URL instead of assuming JPEG, so export doesn't silently corrupt a figure the same way if the format ever changes again. **Only one live paper had any figures at the time this was found** (the reported 16-page one) — no data migration/backfill was run; re-parsing that paper (the existing "Re-parse paper" action) regenerates it through the fixed pipeline.
- **Slow upload/parse on a multi-page PDF.** Two independent fixes: (1) `useGeneratedPapers.parseExistingPaper` was uploading each rasterized page to Storage **sequentially** (one `await` per page in a `for` loop) — changed to upload all pages **in parallel** via `Promise.all` (order-preserving, so `content_upload_ids` still comes out correct). (2) `rasterizePdfToImages` was rendering each page to an **uncompressed-ish PNG** — several MB per page at `RENDER_SCALE = 2` for a text-heavy exam page — switched to **JPEG q0.85**, which is a large size cut for essentially no OCR/multimodal-reading quality loss (rendered pages aren't photos, but they're not being edited either — same tradeoff a phone camera photo already makes) and speeds up both the browser→Storage upload here and the edge function's later Storage→Gemini re-upload of the same bytes. `PARSE_FILE_TYPE_MAP`'s `type: "png"` for a rasterized page was updated to `"jpg"` to match.

Deployed `parse-homework-paper` v8 (PNG figures).

**Second cut-off fix — crop padding (2026-07-14):** even with valid PNG bytes, figures were still reported cut off. The remaining cause is the model's `box_2d` being drawn too tight (it hugs the plotted lines and drops the outer axis numbers / grid frame), so the crop clipped the diagram's edges. `cropFigureFromImage` previously padded the box by a flat 3% of its own size — too little for a small or tightly-drawn box. Padding is now `max(8% of the box side, 15/1000)` on each axis (the absolute floor gives a small box meaningful breathing room), still clamped inside the page. Grabbing a sliver of surrounding whitespace is far better than clipping the figure. Deployed `parse-homework-paper` v9.

**Still not yet exercised end-to-end against live Gemini from the build sandbox** (same egress caveat as every phase) beyond the one live parse that surfaced the above — whoever picks this up next should re-run a multi-page parse to confirm the upload speed-up, PNG figures, and the wider crop padding all land as expected, and still sanity-check per the point above: (1) Gemini reaching for a Markdown table over prose for real tabular questions, (2) bounding-box tightness, (3) a HEIC photo end-to-end.

## No-repeat generation + English question wording + review/builder polish (2026-07-14)

Four changes from live teacher use, `generate-homework-paper` **v23** plus frontend.

- **No-repeat generation (`generate-homework-paper`).** The `question_bank` hash cache used to **reuse** a prior row's text/answer on a hash hit ("real cross-paper dedup"), which meant regenerating a paper — or building another for the same student — kept returning the *same* questions, the opposite of what a teacher hitting "Regenerate" wants. Fixed two ways:
  1. `materializeQuestion` no longer reads back on a hit — it always uses the freshly generated question. `question_bank` is now **written-only** (a record, best-effort insert; a duplicate hash just no-ops).
  2. A new `loadPriorPrompts(client, paper)` gathers every question prompt already set for this student (across all their papers, including the current one), deduped and capped at `MAX_AVOID_PROMPTS = 80`, and `buildAvoidNote` feeds them into every block's prompt as an explicit "do NOT reuse or lightly reword any of these" list. So generation actively steers away from repeats instead of drifting back to them. `PaperRow` gained `student_id` for the lookup. Runs as the calling teacher (RLS), so the avoid-list is naturally scoped to papers the teacher can see.
- **Question wording is generated in English.** A language-acquisition paper (e.g. IBDP French B) was generating the *entire question stem* in the target language ("Comment demander …"), unreadable for a beginner. The block prompt now instructs Gemini to write every question's instruction/stem and the mark scheme **in English**, with only the material actually being tested (the target-language words/phrases/options a language question turns on) left in the other language. The `looksLikeAQuestion` target-language command-word support (added earlier for the French-B validation failure) is left in place — harmless now that stems are English, and still a backstop.
- **Removed every AI-regenerate control from the review page** (`TeacherHomeworkReviewPage.tsx` + `QuestionReviewCard.tsx`). Teacher feedback: regenerate "doesn't work / isn't wanted." Gone are the block-level **Regenerate block**, the per-question **Regenerate**, and the footer **Regenerate all** — leaving inline **Edit** and **Confirm & Publish** as the review actions. `QuestionReviewCard` dropped its `busy`/`canRegenerate`/`onRegenerate` props. **Retained:** the failure-state **Retry generation** card (so a paper that errored can still be re-run) and, for parsed papers only, the footer **Re-parse paper** action (re-running extraction is not "regenerate"). The edge function's `regenerate_block`/`regenerate_question` scopes are left in place but are now unreachable from the UI — no backend change.
- **Trimmed builder copy** (`TeacherHomeworkPage.tsx`). Removed the explanatory subtitles under the Subject / reuse-a-paper / upload-a-past-paper cards and shortened the upload labels ("Upload material (PDF recommended — indexed into chapters/sections)" → "Upload material", "Reuse a previously uploaded file (any student)" → "Reuse a previous upload"), per feedback that the page had too much text.

### Duplicated MCQ option labels — "A. 1. Fourth" (2026-07-14)

An MCQ block came back with every option carrying its own ordinal prefix ("1. Fourth", "2. Third", …) while the UI renders its own A/B/C/D label — so options read "**A. 1. Fourth**". (Distinct from the earlier "A. A vacuum" note, which was a genuine answer coinciding with its label — this is the model literally baking an enumerator into the option text.) Fixed at two layers, both using the same leading-enumerator regex (`stripOptionPrefix`/`stripOptionLabel`, which only strips a token followed by a delimiter — `1.`/`2)`/`A.`/`(a)`/`- ` — so a real answer like "A vacuum" or "1984" is left alone):
- **Generation** (`generate-homework-paper` **v24**): a prompt instruction telling the model to give the option text only (no number/letter/bullet prefix), **plus** `materializeQuestion` strips any prefix from `options` before storing — so the stored `questions_json`/`question_bank` are clean.
- **Display** (`stripOptionLabel` in `src/utils/homeworkGrading.ts`): applied where options render — `QuestionReviewCard`, `QuestionAttemptCard`, `TeacherPaperResults`, `exportHomeworkPaper` (PDF + DOCX) — so **already-stored** papers (and parsed papers, which don't go through the generation strip) display correctly without regeneration. Grading is unaffected — MCQ/true_false grade by the `correct_option` index, never the option text.

## Manual photo/PDF answer grading (2026-07-14)

Teacher request: some subjective/math work is faster and more natural for a student to hand-write and photograph than to type — and for that kind of answer, the teacher wants to grade it themselves rather than trust an AI reading of handwriting, the way a marked-up paper normally works (margin comments + a hand-written total). This adds exactly that, as a genuine alternative to typing, never AI-graded.

### The flow

```
Student attempting a subjective question -> "Write answer" / "Upload a photo" toggle
        -> photo uploaded to the private homework-answers bucket
        -> (or, instead of answering question-by-question) attach ONE PDF covering
           the whole worked solution -> never split/parsed, stored as-is
        -> Submit -> grade-homework-submission auto-grades MCQ/fill-blank as normal,
           AI-grades any other still-typed subjective question as normal, and writes
           a PENDING placeholder for anything photo/PDF-answered (awarded 0)
        -> Teacher opens the review page. A per-question PHOTO answer is shown
           inline (click anywhere to drop a text comment, enter the mark). A
           whole-paper PDF is NOT shown inline — it shows a "View & annotate PDF"
           button that opens its own full-page route
           (/teacher/homework/:paperId/whole-paper, TeacherWholePaperReviewPage)
           where the teacher reads the pages, drops comment pins, enters the mark,
           and publishes -> Publish grade (same gate as every other grade)
```

### Data model

- **`submissions.whole_paper_answer`** (`{ file_url, file_name } | null`, new jsonb column, migration `20260728010000_homework_manual_answer_grading.sql`) — set when the student attaches one PDF covering their whole worked solution instead of answering subjective questions individually. It covers **every subjective question at once** (deliberately not scoped per-question — see "Deliberate scope" below); objective (`mcq`/`true_false`/`fill_blank`) questions are answered and auto-graded exactly as before, regardless of whether a whole-paper PDF is also attached.
- **`answers_json`'s `HomeworkAnswer`** (`src/types/database.ts`) gained a photo variant with no schema change (already jsonb): `{ kind: 'photo', files: [{ file_url, file_name }] }` for any individual subjective question — a genuine alternative to typing on that one question, toggled per-question in `QuestionAttemptCard.tsx`. `isPhotoAnswer()` is the type guard used everywhere this needs branching (attempt UI, review UI, and the edge function's own local copy).
- **`grades.whole_paper_grade`** (`{ awarded, max, annotations: Annotation[] } | null`, new jsonb column) and **`per_question_json[qid].graded_by: 'manual'`** (a third value alongside the pre-existing `'auto'`/`'ai'`, plus an optional `annotations` array on `QuestionGrade`) are the manually-graded counterparts. **Neither is ever computed by Gemini.** `grade-homework-submission` writes a *pending placeholder* the first time it sees a photo/whole-paper answer — `awarded: 0`, `max` = that question's marks (per-question) or the sum of every subjective question's marks (whole-paper) — and a **re-grade preserves an already-entered manual mark and its annotations as-is** rather than resetting them (fetches the existing `grades` row up front and carries the manual entries over; only `max` refreshes, in case the paper's marks changed). This is the one deliberate exception to "a re-grade overwrites the grade row" — everything AI/auto-graded still gets fully recomputed and its review/publish state cleared as before, but a teacher's own hand-entered work on a photo/PDF answer was never AI output to begin with and must never be silently wiped by clicking "Re-grade with AI" to fix something else on the same paper.
- **`Annotation`** (`{ id, x, y, text, page?, file_index? }`) — a single comment pin, `x`/`y` as percentages (0–100) of the rendered image/page so a pin's position survives any display size. `page` disambiguates a multi-page whole-paper PDF; `file_index` disambiguates a per-question answer with more than one attached photo.
- **New private `homework-answers` storage bucket** — a student's own uploaded answer files, mirroring `report-cards`' self-upload shape (INSERT/SELECT scoped to the student's own `students.id` folder) plus `homework-content`'s staff-read shape (any `teachers` row can `SELECT`, so the paper's owning teacher/coach/admin can open a submitted answer). Deliberately a **new** bucket rather than reusing `homework-content` — that bucket's storage policies are staff-upload-only (`content_uploads` is teacher-supplied source material), and a student uploading their own answer is a different actor with a different access shape, same reasoning `report-cards` already established for the report-card upload.

### `grade-homework-submission` changes (redeployed v12)

- Subjective questions are now split three ways before grading: **AI-gradable** (still typed, no whole-paper PDF) go through the existing single-batched-Gemini-call path unchanged; **photo-answered** questions are excluded from that batch entirely and get the manual placeholder; **whole-paper-covered** questions (when `submissions.whole_paper_answer` is set) are *all* excluded from the batch and get no `per_question_json` entry at all — the mark lives on `grades.whole_paper_grade` instead, not spread across per-question entries that would have nothing meaningful to show individually.
- The existing-grade-row fetch (for manual-mark carry-over, see above) is a plain `select` before the main grading pass — cheap, and only reads `per_question_json`/`whole_paper_grade`, not the whole row.
- `totalMarks`/`maxMarks` now fold in `whole_paper_grade.awarded`/`.max` alongside the per-question sum, and the client-side `gradeEffectiveTotal`/`gradeMaxTotal` (`src/utils/homeworkGrading.ts`) were changed to take the whole `Grade` object (not just `per_question_json`) for the same reason — every call site (`TeacherPaperResults`, `HomeworkResultsList`, `StudentHomeworkPage`, `StudentHomeworkAttemptPage`) was updated to pass `grade` instead of `grade.per_question_json`.

### Frontend

- **`AnnotatableMedia`** (`src/components/homework/AnnotatableMedia.tsx`, new) — the shared click-anywhere-to-comment overlay, used both for a per-question photo and a whole-paper PDF (as an array of page images). Click the rendered image (when `editable`) to drop a pin at that spot and type a comment; click an existing pin to view it, with a Remove action when editable. Deliberately simple (no drag-to-reposition, no rich text) — a text comment pinned to a point is the whole ask, not a full annotation toolkit.
- **`src/utils/homeworkAnswerMedia.ts`** (new) — upload (`uploadHomeworkAnswerFile(s)`) and signed-URL resolution (`resolvePhotoAnswerUrls`, `resolveWholePaperPageImages`) for the `homework-answers` bucket. A whole-paper PDF is rendered to page images for display via a new `renderPdfPagesToDataUrls` in `src/utils/rasterizePdf.ts` — the same `pdfjs-dist` machinery the "parse an existing paper" flow already uses to rasterize a PDF, reused here purely for on-screen viewing (a signed URL in, image data URLs out) rather than producing upload `File`s.
- **`QuestionAttemptCard.tsx`** — every subjective question now shows a **"Write answer" / "Upload a photo"** toggle (hidden once submitted). Switching modes clears whatever was in the other mode, so there's never an ambiguous typed-text-plus-attached-photo state. Once graded, a photo answer renders through `AnnotatableMedia` (read-only) with the teacher's pins instead of AI feedback/per-point breakdown, since `graded_by: 'manual'` questions never have those.
- **`StudentHomeworkAttemptPage.tsx`** — an "Attach your whole worked solution as one PDF" card (shown whenever the paper has at least one subjective question), independent of the per-question toggles above. It's rendered at the **TOP** of the page, above the questions list (was originally at the bottom), so the student sees "hand in written work as one PDF" as the primary option before scrolling. Once a PDF is attached the card shows **"Uploaded as a file: <name>"** and the pre-submit dialog no longer nags about unanswered questions at all — it says the worked solution is attached instead of showing an "N unanswered" count (previously it only excluded subjective questions from the count). Once graded, renders the PDF read-only via `AnnotatableMedia` with the teacher's comments + the hand-entered mark.
- **`TeacherPaperResults.tsx`** — a photo answer renders via `AnnotatableMedia` (editable for the paper's own teacher, read-only for a PC per the existing `isCoach` gate) in place of the plain text `StudentAnswer` display. A whole-paper PDF is **not** shown inline: it gets a small `WholePaperReviewLink` card (above the per-question list) showing the current mark + comment count and a **"View & annotate PDF"** button that opens the dedicated review route. The mark-entry + annotation UI moved off this page onto that route. The existing `OverrideControl` is still reused for a manual per-question (photo) mark, with its button labels adjusted for `graded_by: 'manual'` ("Enter mark"/"Clear" instead of "Override"/"Reset to AI" — there's no AI baseline to reset to).
- **`TeacherWholePaperReviewPage.tsx`** (`src/pages/teacher/`, new; route `/teacher/homework/:paperId/whole-paper`) — the full-page whole-paper PDF review. Loads the submission/grade via `useSubmissionGrade` and the paper via `useGeneratedPaper`, renders every PDF page through `AnnotatableMedia` (editable for the owning teacher, read-only for a PC), and hosts the mark-entry control (awarded/max, both editable — "scaled to the actual marks, but the teacher can adjust") plus its own "Publish grade to student" button, so the teacher can review, comment, mark, and publish without returning to the results tab. If the submission isn't graded yet (no `whole_paper_grade`), it points the teacher back to the Student's Answers tab to grade first.

### Deliberate scope / follow-ups

- **A whole-paper PDF is genuinely a PDF only** (not a photo or several photos) — matching the specific ask; a student who prefers to photograph a whole paper still answers question-by-question with a per-question photo on each subjective question instead. Could be extended to accept multiple images (à la the teacher's parse-a-past-paper flow) if that turns out to matter in practice.
- **AI grading was deliberately kept out of both paths entirely**, not offered as an optional first-pass a teacher could accept/reject. This was a direct product decision, not a technical limitation — Gemini vision could plausibly grade a photographed answer the same way `parse-homework-paper` already reads a marked answer key off a page, but the explicit ask was "teacher grades directly," so that's what's built. Revisit if teachers find fully-manual grading too slow at volume.
- **Not yet exercised end-to-end against live Gemini/a live upload from this sandbox** (same egress caveat as every phase in this doc) — `tsc -b`/`vite build`/lint pass clean and both edge functions were redeployed and read back to confirm they match the local source, but no one has clicked through a real photo upload + annotation + publish cycle yet. Whoever does that first pass should also sanity-check the `AnnotatableMedia` pin positions survive a page reflow/resize (percentage-based, should hold, but worth eyeballing on a real phone-width screen) and that a signed URL's 1-hour TTL (`homeworkAnswerMedia.ts`) doesn't expire mid-review on a long grading session — if that turns out to matter, the fix is re-resolving on demand rather than caching the signed URL client-side, which is already what happens today (each mount re-signs).

## Parse-format follow-up, photo answers on every type, reuse-picker + PDF-review polish (2026-07-14)

Five fixes from live teacher/student use. `parse-homework-paper` and `grade-homework-submission` changed (both need redeploy); the rest is frontend-only. No schema change.

- **Parsed papers: group by the paper's own question number.** `EXTRACTION_PROMPT` was emitting each labelled sub-part ((a), (b), (i), (ii)…) as its *own* question object, so a single numbered question came back split across several cards. The prompt now makes it an explicit hard rule: **exactly ONE question object per top-level printed number (1, 2, 3, 4…)**, with every sub-part, lead-in, and table for that number combined into that one object's `prompt`; a numbered question is classified by its *overall* shape (only a whole-question single MCQ/fill-blank stays that type, otherwise it's a mark-scheme question whose points cover every sub-part). The classify bullet was rewritten to match so it no longer contradicts the grouping rule.
- **Parsed papers: data tables render as real tables, not a run-together line.** The prompt already asked for a Markdown table, but Gemini sometimes emitted the whole table **inline on one line / inside the sentence**, which `react-markdown` + `remark-gfm` (both need a block-level table — header + `|---|` separator + each row on its own line) then rendered as collapsed text. Two changes: (1) the table formatting instruction now insists the table be block-level with a blank line before/after and **every row on its own line, never inline**; (2) a defensive `reflowInlineTables()` in `parse-homework-paper` (`normalizeQuestion` runs every extracted `prompt` through it) detects a collapsed single-line pipe-table — a `|---|` separator with table content on the same line — and rebuilds it onto proper lines (column count from the separator, joint-empty cells between rows dropped, genuinely-blank fill-in cells preserved, prose before/after the table split onto their own lines). Conservative: an already-well-formed multi-line table and anything it can't parse confidently are returned unchanged. This fixes both the on-screen render and the PDF/DOCX export (both read the same stored Markdown).
- **A photo answer is now allowed on EVERY question type, not just subjective.** `QuestionAttemptCard` shows the **"Write/Select answer" / "Upload a photo"** toggle for MCQ and fill-blank too (a student can photograph hand-worked working for any question). In `grade-homework-submission`, the `isPhotoAnswer(ans)` check was **hoisted above the auto-grade branches** so a photo answer on an MCQ/fill-blank is written as a `graded_by:'manual'` pending placeholder (teacher-marked) instead of being auto-marked wrong against the object. The whole-paper-PDF-covers-subjective check was hoisted alongside it. `TeacherPaperResults` already renders any photo answer via `AnnotatableMedia` + the manual `OverrideControl` regardless of question type, so the teacher side needed no change.
- **Reuse-a-previous-upload picker hides parsed past-paper pages.** `useTeacherUploads` (the "Reuse a previous upload" dropdown in the generate-from-upload flow) was listing *every* `content_uploads` row for the teacher, including the 15-20 rasterized page images each parse-an-existing-paper upload creates — swamping the picker. It now restricts to document file types (`pdf`/`ppt`/`pptx`/`docx`, which is all the material-upload/index flow ever creates, so every rasterized page image is excluded) and additionally drops any upload referenced by a `content_source_type='parsed'` paper (the rare raw-PDF parse fallback). Frontend-only — RLS/storage already scope by `uploaded_by_teacher_id`.
- **Whole-paper PDF review: reachable, markable, and not oversized.** `TeacherWholePaperReviewPage` used to dead-end on an ungraded submission with "go to the other tab and click Grade now" (which read as "there's no edit button"). It now has an inline **"Grade now"** button that prepares the paper for marking in place; the mark-entry control is a prominent primary **"Enter mark by hand"** button (was a tiny ghost link); and the PDF pages are capped via a new `AnnotatableMedia` `maxWidthClass` prop (`max-w-3xl`, centred, bumped from an initial `max-w-2xl`) instead of rendering full-width-huge.

## `AnnotatableMedia` rework — zoom, Google-Docs-style margin comments, and a dedicated per-question photo review route (2026-07-15)

A run of follow-ups from live teacher feedback on the whole-paper PDF review page, ending with the same treatment extended to per-question photo answers. All in `src/components/homework/AnnotatableMedia.tsx` unless noted — every consumer (whole-paper PDF, per-question photo review, student's own read-only view) shares this one component, so a fix here applies everywhere at once.

- **+/− zoom (50%–200%, 25% steps, Reset).** Each page/photo's width is a percentage of the surrounding scroll region, which has `overflow-x-auto` so a zoomed-in page pans instead of clipping. Click-to-comment position math is unaffected — it reads `getBoundingClientRect()` of the actual rendered page box, which already reflects the current zoom/scroll state.
- **Comments moved into a margin, not a popup anchored to the click point.** The first cut used a floating box positioned at the click's `x%/y%` — for a click near the right or bottom edge, the fixed-width box ran off the page (reported directly: "the box is going out"). A first fix flipped the box to the opposite side when there wasn't room; a follow-up request asked for the box to disappear entirely in favour of **true Google-Docs-style margin comments** — each comment card sits at the exact same `top: y%` as its pin (the margin column is stretched via flex to match the page's own rendered height, so the same percentage lines up on the same line on both), rather than a flat scrolling list disconnected from where the pin actually is. Clicking a pin or its card highlights and (on the narrow-screen list fallback only) scrolls to the other. The margin is only offered when the caller passes `maxWidthClass` (i.e. the "full page" usages — the whole-paper PDF and, as of this same day, the new per-question photo route below); compact embedded usages fall back to a plain list under the image, unchanged from before this rework.
- **The margin must never shrink the page.** An intermediate version reserved a fixed 256px (margin width + gap) out of the page's own zoomed width — which made the page render *smaller* than before the margin feature existed at all (reported directly). Fixed: the page always renders at its full requested size (`${zoom}%` of the reading column) regardless of whether a margin is shown; the margin is purely additional width beside it, and if the two don't both fit, the existing `overflow-x-auto` scrolls rather than the page being squeezed.
- **The "click anywhere…" banner was dropped entirely** per feedback that a persistent tinted instruction box read as a watermark.
- **Images get real padding, not edge-to-edge.** The image used to butt directly against its bordered card's edge. Restructured into an outer decorative box (border + padding + rounded corners) wrapping an inner box that tightly hugs the image with no padding of its own — click/pin-position math stays keyed to the inner box (unaffected by the visual padding on the outer one), so pin accuracy didn't need to change.
- **A photo answer now opens on its own dedicated review route, matching the whole-paper PDF.** New `TeacherQuestionPhotoReviewPage.tsx` at **`/teacher/homework/:paperId/question/:questionId`** (registered in `App.tsx`) — the same shape as `TeacherWholePaperReviewPage`: loads the question + its photo answer, shows a "Grade now" prompt if the submission hasn't been graded yet, a mark-entry control (`awarded` editable via `useSubmissionGrade.overrideMark`, `max` fixed at the question's own marks), the image(s) via `AnnotatableMedia` with the margin/zoom treatment (`maxWidthClass="max-w-3xl"`), and its own "Publish grade to student" button. `TeacherPaperResults.tsx` no longer renders a photo answer inline at all — a photo-answered question shows a small `PhotoAnswerReviewLink` card (mirroring the existing `WholePaperReviewLink`) with the current mark + comment count and a "View & annotate photo" button; the inline per-question `OverrideControl` is hidden for photo-answered questions since mark entry now lives exclusively on the dedicated route. Read-only for a PC who doesn't own the paper, same as every other grading surface.

## Parsed papers: paper-level and section-level instructions, and per-question topic labels (2026-07-15)

Teacher feedback showed a parsed past paper (an IB-style exam) losing everything that wasn't itself a question: the cover page ("Instructions to candidates", time allowed, max marks), each section's own instruction line ("Answer **all** questions in this section..."), and the little topic subheading printed above an individual question (e.g. "Biological approach to understanding behaviour" above one question in a mixed-topic section). All three are now captured — as read-only context, never as answerable questions — while the actual answerable questions are completely unaffected.

- **Schema-free, additive JSON.** No migration — both new fields are optional keys inside existing jsonb columns, the same pattern `figures` used earlier: `GeneratedPaperContent.paper_instructions?: string` (inside `questions_json`) and `PaperBlock.instructions?: string` (inside `blocks`). A per-question topic label needed no new field at all — it's folded into that question's own `prompt` as a bold Markdown heading line, the same "prompt is Markdown" mechanism tables/emphasis already use.
- **`parse-homework-paper` (`EXTRACTION_PROMPT` + `parseResponseSchema`, redeployed).** Four new prompt rules: (1) transcribe the paper's own front matter (subject/level, date, time allowed, "Instructions to candidates", max-mark statement) into a new top-level `paper_instructions` field as Markdown, **explicitly excluding copyright/licensing/publisher boilerplate** — a real IB paper's Spanish-language copyright block is exactly the kind of text this must never surface; (2) transcribe a section's own instruction text into that section's new `instructions` field, verbatim, never repeated inside a question; (3) keep a per-question topic label as the first (bold) line of that question's `prompt`; (4) never turn any of the above into a question object. `buildContent()` reads `sec.instructions` onto each built `PaperBlock`; the retry loop in the `serve` handler reads `result.paper_instructions` from whichever Gemini call actually succeeds and attaches it to the final `PaperContent`.
- **`useGeneratedPaper.saveQuestions` data-loss fix.** `TeacherHomeworkReviewPage.handleSaveQuestion` (a plain inline edit of one question) used to build `{questions, total_questions, total_marks}` from scratch and call `saveQuestions()`, which replaces the *entire* `questions_json` column with exactly what it's given — silently dropping `paper_instructions` (and any other future top-level field) the first time a teacher edited any question after this feature shipped. Fixed by spreading the existing `content` object first, so only the three changed fields are actually overridden.
- **Rendering.** `TeacherHomeworkReviewPage.tsx`: `paper_instructions` renders once at the top of the Question/Answer Sheet tabs (not shown on Student's Answers), and `block.instructions` renders under each block's existing header, both via the shared `QuestionMarkdown` renderer. `StudentHomeworkAttemptPage.tsx` gained the same `paper_instructions` card plus block-grouped question rendering (previously a flat list) — a section header + its instructions only appear when there's more than one block or the block actually carries instruction text, so a plain single-block generated paper's page is visually unchanged; a multi-block **generated** paper's header goes through the same `styleName()` template-code → friendly-name lookup the teacher page already uses (a parsed paper's section title is already human-readable text, so the lookup harmlessly no-ops for it).
- **Not yet done:** `TeacherPaperResults.tsx` (the grading/results view) and PDF/DOCX export do not yet surface `paper_instructions`/`block.instructions` — reasonable follow-ups if a teacher asks for them, deliberately out of scope here since the results tab is about reviewing answers already given, not re-reading the paper.

## Parsed papers: case-study line numbers rendered in a margin gutter (2026-07-16)

Teacher feedback (with a screenshot of a parsed CIE/IGCSE business-studies paper): a case study that has **line numbers down the left margin** (5, 10, 15, 20, … every fifth line, so a question can say "refer to line 33") came back **unreadable** — those margin numbers were stranded INLINE in the flowing prose ("…clean up after a festival at an average **10** cost of $250 000…"), reading as if the numbers were part of the sentences. Root cause: `EXTRACTION_PROMPT` already tells Gemini to keep the margin numbers "at the very start of the line it labels", but Gemini collapses the intra-paragraph line breaks into flowing text, so each number lands mid-sentence where its physical line used to begin. The teacher wanted the numbers **kept** (they're real line references) but visually separated so they stop blending into the words.

Fix is **frontend rendering only** — no schema, no edge function, no re-parse needed. It reads the numbers straight off the already-stored transcription (wherever Gemini left them) and pulls them into a distinct left-margin gutter, so existing parsed papers are fixed the moment the frontend deploys, and a passage with no line numbering is completely untouched.

- **`src/utils/lineNumberedText.ts`** (new) — `splitLineNumberedText(text)` detects the margin-number sequence and splits the passage into gutter rows (`{ n, text }`). Detection is deterministic and conservative: it scans for short standalone integers that label a line (a 1–3 digit number not part of a larger token — so `$100`, `2016`, `3.5`, `COVID-19`, the `000` of `25 000`, and `20%` are all excluded — followed by whitespace then a non-digit), then keeps only the longest chain whose values form an ascending arithmetic progression (5,10,15…, or 1,2,3…, or 10,20,30…) consumed in document order, skipping content numbers that fall between real markers ("60 stages", "300 miles"). It requires ≥3 markers starting near the top (first value ≤ 2·step), so an incidental "5 apples, 10 oranges, 15 pears" is the only realistic false-positive — and even then the cost is just three numbers shown in the gutter, never mangled or dropped text. Returns `{ numbered: false, rows: [whole text] }` (a no-op) when no sequence is found. Unit-verified against the reported paper's transcription: all 11 markers (5…55) detected, zero false positives from its many content numbers.
- **`QuestionContent.tsx`** — new `LineNumberedMarkdown` renders each row as a flex line: a fixed-width, muted, monospace, right-aligned gutter number + the row's Markdown text (same `remark-gfm`/`remark-breaks`/component set as everywhere else). A new **`StimulusContent`** export wraps it + `QuestionFigures`, mirroring `QuestionContent` but for a section's shared stimulus/case study. Falls straight back to `QuestionMarkdown` when the passage isn't line-numbered.
- **`TeacherHomeworkReviewPage.tsx` / `StudentHomeworkAttemptPage.tsx`** — the section stimulus (`block.stimulus`) now renders via `StimulusContent` instead of `QuestionContent`. Question **prompts** still use `QuestionContent` (only the shared case study carries margin line numbers, never the questions themselves), and the export path is unaffected (`exportHomeworkPaper.ts` never included the stimulus).
- **Deliberately not changed (rendering fix):** `EXTRACTION_PROMPT` / the edge function were not touched *for the gutter*. The renderer normalizes the numbers regardless of where Gemini leaves them, so no re-parse is required and no prompt-tuning risk is taken on; the "keep the margin numbers" instruction there is still correct and still feeds this. Line numbers can't align to a fixed physical line in a reflowing web view either way — the gutter gives the reference number next to the text it labels, which is what the reference is actually for.

## Parsed papers: recover a dropped case study (2026-07-16)

Immediately after the gutter fix above, a second live report on a different paper (an IB Business Management Paper 1, 5 photographed pages, paper 38): the **case study was missing entirely** — every question cited it ("line 33", "line 18", "lines 38–50") but no `stimulus` was captured on any section, and it wasn't hiding in `paper_instructions` or folded into a question either. Verified against the live row: all 5 pages uploaded and parsed, front matter + all 8 questions extracted, but the "Before One PLC (BON)" passage simply dropped. This is Gemini non-determinism (the same source parsed *with* its case study on an earlier paper) — the model transcribed the questions and skipped the multi-page stimulus prose, despite the existing "DO NOT DROP IT" instruction. **Unrelated to the gutter change** (which only *renders* a stimulus that exists and wasn't even deployed to prod yet).

Fix in `parse-homework-paper` (deployed **v15**), no schema / frontend change:
- **A deterministic recovery retry.** The extraction loop (now `MAX_EXTRACTION_ATTEMPTS = 3`, was 2) checks after each pass: if the extracted questions reference shared source material (`referencesSharedSource` — a high-precision regex for line citations `\blines?\s*\d` or "case study") **but no section carried a `stimulus`**, it re-invokes Gemini with a forceful `STIMULUS_RECOVERY_NOTE` telling it exactly what it dropped and where to look (usually an earlier page). The best result so far is always retained, so a retry that still can't find the stimulus ships the questions rather than losing them — the guard can only add a stimulus, never fail the parse. The existing "no questions at all" retry is folded into the same loop.
- **Prompt reinforcement.** A new `EXTRACTION_PROMPT` "WHERE TO FIND IT" bullet and an added `MULTI_PAGE_NOTE` line both stress that the case study is frequently on its *own* / earlier page, separate from the questions, and must be transcribed wherever it sits.
- **Recovery path for the affected paper:** clicking **"Re-parse paper"** on a paper whose case study was dropped now re-runs extraction through this guard. (The margin-gutter rendering of that recovered case study only shows once the frontend branch is deployed too — see the gutter section above.)

## Operational notes carried over from the original design

- **Async everywhere**: generation and file parsing are slow — treat as background jobs with a pollable status, never a blocking request. Phase 4 does this via a fire-and-forget edge-function invocation + client-side polling on `generated_papers`, not a queue — fine at this volume, but revisit if generation volume ever makes 4s polling too chatty. **Dead-worker guard (2026-07-14):** because the invoke is fire-and-forget, a worker the platform hard-kills (a 504/OOM at the ~150s wall-clock limit) never runs its own catch, so it writes no `generation_error` and the "Generating…/Parsing…" badge would spin forever. Both poll loops (`useGeneratedPapers` list, `TeacherHomeworkReviewPage` review) now time each pending paper from first sight and, past `GENERATION_TIMEOUT_MS` (240s, matching the indexing flow's grace window in `useContentUpload`), write a timeout `generation_error` client-side so it surfaces as failed-with-retry. The write is conditional (`questions_json`/`generation_error` still null) so it can't clobber a paper that just finished.
- **Grading trust**: subjective mark schemes must be specific gradeable points, not free text, or Phase 7's LLM grading has nothing concrete to check against. Teacher override must stay one click.
- **PPT/PPTX/DOCX uploads still aren't generatable** (Phase 4 scope decision — see that section) — Phase 5's review UI and any future upload-flow polish should surface that limitation clearly rather than let a teacher discover it only after generation fails.
