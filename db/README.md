# db/

Ascend Now database — Supabase/PostgreSQL.

**This has been consolidated.** The 28 numbered files that used to live in `schema/` and the 35 timestamped files that used to live in `../supabase/migrations/` were two overlapping, out-of-sync change logs whose own migration-tracking table was empty (meaning neither could be trusted as an accurate history of the live database). Both have been deleted and replaced with a single migration, generated directly from the live database rather than from replaying history:

**`../supabase/migrations/20260701000000_baseline_full_schema.sql`** — reproduces the entire live schema: every table, constraint, index, function, trigger, RLS policy, grant, and storage bucket/policy, exactly as introspected from the live project on 2026-07-01. It's schema-only (no data). One gap found during that audit — `zoom_invoices` was missing base grants for `authenticated`, so its RLS policies couldn't actually fire — was confirmed and fixed immediately after, live and in the repo, via `20260701000001_fix_zoom_invoices_authenticated_grant.sql`.

Going forward, **this is the only migration system for this project.** New schema changes should be added as new timestamped files in `supabase/migrations/`, applied via the standard Supabase CLI (`supabase db push`) or Supabase MCP `apply_migration`, so the migration-tracking table stays accurate this time.

## Structure

```
db/
├── scripts/    — utilities (create an admin, promote a user, seed/reset/wipe data)
└── docs/       — verified live state + historical debugging notes
```

`scripts/wipe-students-and-testing-data.sql` clears every student-related row (students, session_logs, packages/topups, invoices, enrollment_requests, pc assignments, pool resolutions, and the student login accounts) for a clean testing slate — run directly via the SQL editor or Supabase MCP `execute_sql`, not a migration. Teachers, admins, and the subject/curriculum catalogue are untouched.

## Setting up a fresh database

Apply `supabase/migrations/20260701000000_baseline_full_schema.sql` to a fresh Supabase project (via CLI `supabase db push` or the SQL Editor). This creates the full schema but no data — seed lookup tables (`program_types`, `course_types`, `subject_categories`, `curricula`, `subjects`, etc.) and create your first admin afterward.

## Student enrollment workflow & package locking (added 2026-07-02; single-login model since 2026-07-07; multi-package/multi-proof since 2026-07-25)

Students are no longer added purely by hand. A coordinator submits an `enrollment_requests` row (new student, or a renewal against an existing `student_id`) from `/admin/students/enroll`, along with one or more package line items (`enrollment_request_packages` — the enroll form's Package section is a repeatable list, so an admin selling/renewing several packages for the same student at once still only creates one request). Submitting triggers the `send-enrollment-invoice` edge function to email **one** invoice summary — listing every package, with a total once there's more than one — plus a `/pay/:token` link (no login required — the link's token is the only access control) to the "send updates to" address (`enrollment_requests.email` — resolves to `notification_email` if one was entered, else `student_email`). Whoever receives it uploads one or more payment screenshots (one file if paid all at once, several if paid in separate transactions) in a single submission via the public `submit-payment-proof` edge function, which stores each in the private `payment-proofs` storage bucket as its own `enrollment_request_payment_proofs` row and flips the request to `payment_submitted`. An admin reviews it from `/admin/enrollments` and calls `review-enrollment-payment` to confirm or reject:

- **Confirm, new student**: creates the `students` row (including `parent_full_name`/`parent_phone_number` as plain fields, `notification_email`, `curriculum`, and `report_card_url` if captured) and a **single** `auth.users`/`public.users` login (from `student_email`, role `student`) — plus the `pc_student_assignments` row, and a `student_packages` + `package_topups` row **per package line item**; emails the student their own random credentials + one combined package confirmation (every package listed, with a total once there's more than one). This login reaches the read-only student dashboard (`/student/*`). As of 2026-09-10 the confirm step also copies `enrollment_requests.parent_id` onto the new student, linking them to a household `parents` account when the enroll form picked one — that parent's own login is created separately and up front by `create-parent-with-user`, never here, so a confirm still creates exactly one login.
- **Confirm, renewal**: for each package line, tops up the student's current **unlocked** package for that course type, or starts a **brand-new, unlinked** package if the only one that exists is locked; emails one combined renewal confirmation (no credentials) to the "send updates to" address and the student's own login email, deduped.
- **Reject**: sets status to `rejected` (does not silently revert to `pending_payment`) with a reason, and re-sends the payment link. A rejected request can be resent again later via the `resend_rejection` action, which re-emails the same rejection reason + link without changing state — used by the "Resend Email" button on rejected rows in `/admin/enrollments`.
- **Edit / Delete while `pending_payment`**: a request still awaiting its first payment (nobody has uploaded a screenshot yet) can be corrected in place from `/admin/enrollments` — editing resends the invoice email with the corrected details — or deleted outright (cascades to its `enrollment_request_packages`/`enrollment_request_payment_proofs` rows). The quick-edit dialog covers contact/invoice metadata only — packages aren't editable inline (same precedent as course type never being editable there), so a wrong package still means delete-and-recreate. Once a screenshot is uploaded (or the request reviewed), the row is part of the audit trail and only Confirm/Reject/Resend apply.

**2026-07-25 — multi-package requests, multi-file payment proofs.** `enrollment_requests.course_type_id`/`hours`/`package_size_label`/`is_bundle_pool_selection`/`bundle_pool_label`/`resulting_student_package_id`/`is_new_package_generation` moved to the new `enrollment_request_packages` table (one row per package, `sort_order` preserving entry order); `payment_proof_url`/`payment_proof_uploaded_at` moved to the new `enrollment_request_payment_proofs` table (one row per uploaded screenshot). Both are straightforward child tables (`ON DELETE CASCADE`, admin-only RLS mirroring `enrollment_requests`, `authenticated`/`service_role` both granted `SELECT, INSERT, UPDATE, DELETE`) — see `docs/VERIFIED_DATABASE_STATE.md` for full column detail. `review-enrollment-payment` resolves each package line independently (same standalone-vs-bundle pool logic as before, just looped per line, so a request can mix a standalone package and a bundle in one go) but still does one finalize + one renewal-request-auto-resolution pass per confirm.

**Package usage-threshold notifications** (`student_packages.notified_50_pct_at`/`75`/`100`, added 2026-07-02): the `notify-package-threshold` edge function fires (fire-and-forget, no JWT) after every non-no-show session-log save from either session-log form, recomputes hours-used for that session's linked package, and emails the student's currently-assigned PC (via `pc_student_assignments`). As of 2026-07-05 it sends one of two distinct alerts: if the package is over its limit (hours used exceeds hours purchased — including a 0-hour placeholder package created by `handle_session_log_package_lock()`'s fallback), it emails the PC on **every** offending session, deliberately never deduped — a real bug found live where a second session against an already-zero-hour package sent nothing at all, since the function used to bail out entirely whenever `total_hours_purchased <= 0`. Otherwise, for a package with real purchased hours that isn't over limit, it keeps the original behavior: emails the first time usage crosses 50%/75%/100%, stamping the corresponding flag so each threshold only ever notifies once until a topup resets all three (`on_package_topup_inserted()` clears them so they re-arm against the new total).

**Package locking** (`student_packages.is_locked`/`locked_at`/`locked_by_user_id`/`locked_hours_used`) is a separate mechanism from monthly-report locking — it freezes one specific package (no more topups, no more session-log changes against sessions linked to it via `session_logs.student_package_id`, auto-assigned by a trigger to whichever package is currently unlocked for that student+course type) rather than a calendar month. Because a student can now have more than one `student_packages` row per course type over time (a locked one plus a fresh renewal), the old `UNIQUE(student_id, course_type_id)` constraint was replaced with a partial unique index scoped to `WHERE NOT is_locked` — only one *current* package per course type at a time, with any number of locked historical ones alongside it.

## Package renewal requests (added 2026-07-09)

A Performance Coach is usually the one who knows when a student's package needs renewing — but only an admin can actually process a renewal (the invoice/payment flow above). `package_renewal_requests` bridges that gap without becoming a second invoice system: a PC submits a request from `/teacher/renewal-requests` (student + course type + optional suggested hours/label/note), which emails every active admin (`notify-renewal-request` edge function) and shows up on `/admin/renewal-requests` as **Awaiting Acknowledgement**. An admin acknowledges it (a plain status flip, no email) so the PC can see it's been seen, then processes the actual renewal the normal way — `/admin/students/enroll` → `review-enrollment-payment`, exactly as any other renewal. That confirm step now also auto-resolves any `pending`/`acknowledged` renewal request matching the same `(student_id, course_type_id)` to **Renewed**, stamping which `student_packages` row resulted, and emails the requesting PC — nobody has to remember to close the loop by hand. Full mechanism and RLS in `docs/VERIFIED_DATABASE_STATE.md`'s `package_renewal_requests` entry.

**As of 2026-07-16, the `/teacher/renewal-requests` form is bundle/pool-aware, matching `/admin/students/enroll`'s own renewal form instead of always asking for a flat course type + hours.** Picking a bundle course type (Foundation Program / All-In-One) the selected student already owns (any unlocked pool with `package_type_id` = that bundle) requires picking which pool needs renewing first (same pool list as `bundle_pool_settings`), and the chosen pool's name gets folded into `package_size_label`. Picking a bundle type the student doesn't already own shows the bundle's fixed pools/hours read-only and skips the hours picker entirely — a first-time bundle request has nothing to guess at, since a first-time bundle purchase always creates the whole fixed set of pools in one shot. No schema change (`package_renewal_requests` itself is unchanged — the pool name is just text folded into the existing `package_size_label` column, same convention `enrollment_request_packages.bundle_pool_label` uses on the admin side, just without a dedicated column here since nothing downstream needs to match on it structurally).

## Multi-pool packages: Foundation Program / All-In-One (added 2026-07-02)

Some packages need several concurrently-active pools of the *same* course type for one student — e.g. Foundation Program is a 10hr general Beyond Academic pool plus a 24hr "Discovery Project" pool; All-In-One is four labeled Beyond Academic pools (Primary/Secondary Project, Extra Hours, Career Exploration) plus a College Counselling pool. "Foundation Program" and "All-In-One" **are** real `course_types` (one reactivated from a pre-existing inactive row, one new) — but only as a **grouping label for a bundle of pools** on `/admin/packages` and invoices, via `student_packages.package_type_id`. The teacher-facing "type of program" dropdown is completely untouched, still just Academic / Beyond Academic / College Counselling — a session's own `course_type_id` always comes from that pick, never from a bundle, so each pool's `course_type_id` is always its real, matching category (Beyond Academic or College Counselling), which is what `handle_session_log_package_lock()` actually matches sessions against.

As of 2026-07-02, bundles are bought/renewed only through `/admin/students/enroll` (the direct-entry package builder on `/admin/packages` was removed along with all other direct hour-entry). A first-time bundle purchase creates all its labeled pools at once at their fixed default hours (`student_packages.pool_label` distinguishes them, `NULL` for the default/general one; the old one-pool-per-course-type unique index was relaxed to one-per-`(course_type, pool_label)`); renewing a bundle the student already owns instead requires picking exactly one pool on the enroll form and adds hours only to it (`enrollment_request_packages.is_bundle_pool_selection`/`bundle_pool_label` as of 2026-07-25, previously the same two columns directly on `enrollment_requests`) — see `db/docs/VERIFIED_DATABASE_STATE.md`'s `enrollment_request_packages` entry for the exact columns.

The problem this creates: when a teacher logs a Beyond Academic session for one of these students, which pool should it deduct from? Subject alone often can't say — the same subject (e.g. "Podcast") can legitimately belong to either pool depending on how the project is framed, and that can change over time. `handle_session_log_package_lock()` handles it without ever blocking the teacher's save or changing the session-log form:
- If the student only has one active pool for that course type (everyone except Foundation/All-In-One students), nothing changes — same as before.
- **As of 2026-07-03**, if a PC has already resolved this exact (teacher, subject) combination before (`session_log_pool_resolutions`), it auto-assigns that pool. This is checked *before* the subject-name match below (reordered from the original 2026-07-02 implementation — see why below).
- Otherwise, if the session's subject name exactly equals one of the candidate pools' `pool_label` (e.g. subject "Career Exploration" vs. an All-In-One bundle's "Career Exploration" pool), that alone is unambiguous — it auto-assigns directly, no PC involved at all, for a brand-new session with no resolution recorded yet.
- Otherwise, the session is saved unresolved (`pool_ambiguous = true`, `student_package_id NULL`) and the `notify-pool-issue` edge function emails the assigned PC to pick a pool from the "Pending Deduction" section — available on the admin student-detail page and, as of 2026-07-02, on the PC's own `/teacher/students/:id` too (scoped to their assigned students) — that choice is cached in `session_log_pool_resolutions` so future sessions from the same teacher on the same subject don't ask again. A PC can also reassign an already-resolved session (writes the same cache — future sessions from that teacher on that subject follow the new pool too), or delete a cached resolution to force it to ask again (e.g. once they know the underlying project changed even though teacher/subject didn't).

**Why the resolution check moved first (2026-07-03):** the trigger recomputes `student_package_id` on every `UPDATE` to a `session_logs` row, regardless of what the application's own `UPDATE` statement tried to set. With the subject-name match checked first (the original order), a PC manually reassigning a "Career Exploration" session to a *different* pool would have that exact reassignment silently reverted the moment the row was next written — the subject name would just re-match the "Career Exploration" pool again, ignoring the resolution row the reassignment had just written. Checking the resolution table first fixes this without changing behavior for the common case: a brand-new session with no resolution yet still resolves by subject name alone, same as before.

**A deeper version of the same bug, fixed 2026-07-03 (later):** reordering the checks above wasn't sufficient on its own, because the trigger recomputed `student_package_id` on *every* `UPDATE` to a session, including one that had already been resolved and deducted from a specific pool long ago. That meant changing a (teacher, subject) → pool assignment, or moving one sibling session to a different pool, planted a landmine: the next time *any other* already-deducted session from that same teacher+subject got touched for an unrelated reason (fixing an hours typo, editing the date), the trigger silently re-ran resolution and dragged that historical session onto the new pool too — even though it had already been correctly counted against the old one. `supabase/migrations/20260703010000_never_reresolve_already_deducted_sessions.sql` fixes this at the trigger level: once a session has `OLD.student_package_id IS NOT NULL` (already resolved) and the update doesn't change which student/course_type it belongs to, the trigger skips resolution entirely and leaves `student_package_id` exactly as the row arrives — whether that's unchanged (an unrelated edit) or an explicit new value (a genuine single-session reassignment, affecting only that one row). Only a still-unresolved session (a new `INSERT`, or one still sitting in `pool_ambiguous`) goes through the resolution logic above.

This split what used to be one `assignSessionToPool()` function (in `src/hooks/useStudentPackages.ts`) into three distinct, correctly-scoped actions, plus a new fourth one:
- `resolvePendingSession` — resolves a still-`pool_ambiguous` "Pending Deduction" session, writes the sticky resolution, and sweeps other still-pending sessions matching the same key.
- ~~`reassignSingleSession`~~ — moved **one** already-resolved session to a different pool. **Removed 2026-07-04**: the UI (a "Move a session to a different pool" list + dropdown on the admin/PC student-detail pages) and this function were deleted outright — reassigning an already-logged session to a different pool is no longer possible at all, by design.
- `updatePoolResolutionTarget` — the dedicated way to change a (teacher, subject) → pool assignment "going forward": updates the resolution row and sweeps only currently-pending sessions matching it; never touches an already-resolved session.
- `createPoolResolution` — lets an admin/PC set up a (teacher, subject) → pool assignment **proactively, before any session has even been logged**, via a "+ Add assignment" form (Project/Teacher/Subject dropdowns, subject options filtered by the chosen project's course type — as of 2026-07-09, College Counselling has real subjects too, see `db/docs/SUBJECT_HIERARCHY.md` §3b) in the "Teacher/Subject → Project assignments" section (renamed from "Pool assignment rules") on both the admin and PC student-detail pages.

The "Pending Deduction" queue (and the `notify-pool-issue` email) shows the session's subject, falling back to its program name when it has no subject at all (e.g. pre-2026-07-09 College Counselling / College Essays sessions, which carried a program type but no subject — new ones carry a real subject) rather than rendering a bare "—".

Separately, if a session's course type has **no** active pool at all, the trigger always creates a fresh zero-hour pool **of that same course type** — never a different one — so the overage shows directly on the correct package (e.g. an Academic pool at "1/0 hrs") rather than bleeding into an unrelated pool. (Until 2026-07-05 this instead borrowed from whatever other active pool the student had, regardless of course type — a real bug: an Academic session for an All-In-One-only student got deducted from a Beyond Academic pool inside that bundle. Fixed in `supabase/migrations/20260705120000_never_borrow_across_course_types.sql`.) Either way `pool_fallback_used = true` and the PC gets an email that a package of that type doesn't exist and needs to be set up; nothing ever blocks the teacher.

## Homework Generator (added 2026-07-08, schema only)

A teacher picks a student, a content source (a `session_logs` row's Fathom transcript/summary, or an uploaded PDF/PPT/DOCX via `content_uploads`), and a paper composition — a mix of question "blocks", each a count + exam-board style (IBDP Section A, IGCSE Extended, MCQ, ...). Generation (Gemini API), review, and publish are not built yet — `generated_papers.status` (`draft` → `published` → `in_progress` → `submitted` → `graded`) and `questions_json` exist but nothing writes to them yet outside a migration. Full phased build plan, including what's deliberately deferred from this first migration (status-transition triggers, embeddings/vector storage), is in **[`docs/HOMEWORK_GENERATOR_ARCHITECTURE.md`](./docs/HOMEWORK_GENERATOR_ARCHITECTURE.md)**.

Table roles: `style_templates` (reference library of prompt fragments per exam format, empty until seeded), `content_uploads` (teacher-uploaded source files + async-parsed text), `generated_papers` (the paper itself — composition, generated content, lifecycle status), `question_bank` (dedup cache keyed by `question_hash`), `submissions` (one per paper, a student's answers, immutable once `submitted_at` is set), `grades` (one per submission, auto+LLM marks with a teacher-override column), `session_insights` (optional structured extraction from a session log to steer generation later). RLS mirrors the existing pattern: admin `ALL`; a teacher gets `ALL` on rows they created (`created_by_teacher_id`/`uploaded_by_teacher_id = my_teacher_id()`); performance coaches get blanket access matching the existing `session_logs` "PCs can read/update everything" pattern rather than being scoped through `pc_student_assignments`; a student can only read their own non-`draft` papers/submissions/grades via `can_view_student()`.

## Coordinator Logs (added 2026-07-29)

A Performance Coach files a periodic coaching check-in per student — goals (Primary Goal + Goal Timeline), progress (Progress Status, Biggest Challenge, Next Action), subject baselines with a final-outcome grade improvement once known, several final-outcome fields (University Placement, Project Achievement, an Evidence Link for Profile Building), 9 star ratings (0-5), renewal/referral signals (Renewal Status, Renewal Timing, Referral Status), an Ideal Outcome, and a Primary Relationship Owner. Admin + PC only — no plain teacher, no student access at all, enforced by RLS (not just the UI).

It's a **repeating** log, same shape as `session_logs`: a PC creates a new dated entry each check-in rather than editing one ongoing row, so the full history is kept. The shared `StudentDetailView.tsx` (`/admin/students/:id` and `/teacher/students/:id`) surfaces this as a 5th **"Coordinator Log"** tab showing the most recent entry's snapshot on top (so logging a new one "just updates that data") with every earlier entry linkable below it as history.

6 of the dropdown fields (Primary Goal, Progress Status, Biggest Challenge, Next Action, Renewal Status, Referral Status) are admin-editable lists rather than hardcoded — one shared `coordinator_log_options` table (discriminated by `list_key`) managed from the Admin Reports **Settings** tab (add/rename/reorder/deactivate, plain text only), same "single admin-editable place" precedent as `no_show_settings`/`bundle_pool_settings`. One other dropdown is deliberately **not** admin-editable, since its exact values were given directly rather than referencing a spreadsheet: Primary Relationship Owner (`devi`/`pc_cc`/`ascend_now_system`) is a fixed CHECK-constrained enum on `coordinator_logs` itself.

Subjects work like a small repeatable sub-form: a PC picks a subject (the same cascading Curriculum → Group → Subject(+Level) picker for Academic, or the flat picker for Beyond Academic / College Counselling, scoped to whichever category the log's Course Type implies) and a baseline score, which appends a `coordinator_log_subjects` row; the final-outcome grade improvement for that subject is filled in on a later edit once known. "Type of program/package" references `course_types` — the same list this app already calls "packages" everywhere else (enrollment, invoicing).

RLS scopes a PC through `pc_student_assignments` (mirrors `package_renewal_requests`/`student_packages`) rather than `session_logs`' blanket-PC-read policy, since a PC must only reach their own currently-assigned students here. Full column/RLS detail in `docs/VERIFIED_DATABASE_STATE.md`'s "Coordinator Logs tables" section.

**Automatic per-package renewal, filed into the log (added 2026-07-15; Upsell Opportunity dropped and Upsell Timing renamed to Renewal Timing 2026-07-16).** Renewal Status and Renewal Timing are **not entered in the log form** — they're automatic and tracked **per package/pool** (a student can hold several packages, each at a different lifecycle point). Each coordinator log carries a set of per-package status rows in `coordinator_log_package_statuses`, snapshotted at log-insert time by `trg_coordinator_logs_snapshot_statuses` (so manual PC logs get the section too). When any package's status changes, `sync_coordinator_log_for_student(text)` (SECURITY DEFINER) files a **new coordinator log** — today's date, everything else carried forward from the latest log (including `primary_relationship_owner`, defaulting to `pc_cc` when there's no prior log) — so the log's append-only history is the dated record of what changed. Fires from `trg_sync_coordinator_log_sp_ins` / `trg_sync_coordinator_log_sp_upd` (on `student_packages` — insert, and the `notified_75/100_pct_at` crossings `notify-package-threshold` stamps) and `trg_sync_coordinator_log_req` (on `package_renewal_requests`); no-op when the per-package set is unchanged. Per package: below 75% → *Not Due*; 75%+ → *Upcoming* (Renewal Timing = month it crossed 75%); an open request against that exact package (matched via `package_renewal_requests.course_type_id`: a standalone/leaf request only matches a standalone package of that course type — `package_type_id is null` — and a bundle-course-type request matches every pool whose `package_type_id` is that bundle; a leaf request never bleeds into a same-named pool inside an unrelated bundle) → *In Discussion*; fulfilled request (pool since reset <75%) → *Renewed*; 100% with no renewal in motion → *Not Renewing*. **Referral Status is the one manual field** in this section; it stays on the form. (This replaced two same-day iterations — an aggregate whole-log approach and a standalone `package_renewal_status_events` table — both dropped.)

**Fixed 2026-07-16:** the loop above only ever iterated the student's *existing* `student_packages` rows, so a still-open renewal request for a course type nothing currently matches (a standalone leaf-type request for a student who only has that type inside a bundle, or a request for a bundle the student doesn't own at all — a genuinely new-package request) had no row to hang `in_discussion` on and never showed up in the log at all. `coordinator_log_package_status_rows()` now also emits a "phantom" row (`student_package_id`/`package_type_id`/`pool_label` all `null`) per distinct `course_type_id` among the student's still-open requests that don't match any existing package — always `in_discussion`. `sync_coordinator_log_for_student()`'s change-signature was fixed to key these by `course_type_id` instead of the (here, null) `student_package_id`, since `string_agg` silently drops a `null` concatenation. See `supabase/migrations/20260731000700_coordinator_log_phantom_package_requests.sql`.

## The one rule to never forget

**RLS policies, base table GRANTs, and sequence GRANTs are three separate layers — each has bitten us on `zoom_invoices` alone.** A correct RLS policy still results in "permission denied" if the role has no base grant on the table (`docs/DEBUGGING_HISTORY.md` has the original story). And if a PK column uses a plain `nextval('...')` default instead of `GENERATED ALWAYS AS IDENTITY`, a table-level `INSERT` grant is *not* enough — the role also needs explicit `GRANT USAGE ON SEQUENCE ...`, which is easy to forget since identity columns don't need it. `zoom_invoices` hit both: missing table grant (fixed in `20260701000001`), then missing sequence `USAGE` (fixed in `20260701000005`, found only when a real teacher's upload failed live). If you add a table with a manual sequence default, grant the sequence too — don't assume identity-column muscle memory covers it.

**This applies to `service_role` too, and it does *not* get a pass just because it bypasses RLS.** `service_role` only had base grants on the handful of tables the three original edge functions happened to touch (`admins`, `program_types`, `session_logs`, `teacher_subjects`, `teachers`, `users`) — a prior version of this doc assumed that gap was harmless because "service_role bypasses grants at the Postgres level," which is simply false. The enrollment-workflow edge functions (2026-07-02) were the first to query `enrollment_requests`/`course_types`/`students`/`student_packages`/`package_topups`/`pc_student_assignments` as `service_role` and every one failed with `permission denied for table ...` until `20260702080000_fix_service_role_grants_for_enrollment_workflow.sql` granted them explicitly (plus, again, `GRANT USAGE ON SEQUENCE students_num_seq TO service_role` for the same reason as above). **Whenever a new edge function is the first thing to touch a given table as `service_role`, grant it explicitly in the same migration — don't assume.**
